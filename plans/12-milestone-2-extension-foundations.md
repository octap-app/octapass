## E. Core: import, URL matching, password rules, local vault

All pure Rust in `octapass-core`, exposed through WASM (additive functions only), with tests and fuzz targets.

1. **Importers** (`import/`): parse files into the item model from plan 11, returning `{ items, warnings, skipped }` with unknown fields kept as custom fields or notes, never dropped.
   - P0: Chrome/Edge/Brave CSV, Firefox CSV, Safari / Apple Passwords CSV, Bitwarden JSON (unencrypted, and password-protected encrypted JSON), 1Password 1PUX and CSV, LastPass CSV (including `NoteType:` secure notes), generic CSV with a column mapping.
   - Authenticators: `otpauth://` lists and Google Authenticator `otpauth-migration://` (protobuf). Attach a TOTP to a login with the same issuer/domain, otherwise create a new login.
   - Fixtures in `crates/octapass-core/tests/import-fixtures/` (synthetic, no real data), covering Unicode, RTL text, multiline notes, quotes, empty fields and 10k rows. Add `cargo fuzz` targets for every parser (they don't need to run in CI).
2. **URL matching** (`matching/`): registrable domain via the Public Suffix List (embed a snapshot with the `publicsuffix` or `psl` crate), match modes (base domain default, exact host, starts with, regex, never), equivalent domains (embed a small default list such as google.com/youtube.com and apple.com/icloud.com), and ranking (exact host > base domain > equivalent). Phishing tests: `paypal.com.evil.io` never matches `paypal.com`. IDNs are normalised to punycode. `http` vs `https` mismatch is flagged.
3. **Password rules** (`rules/`): parse Apple's `passwordrules` syntax (`minlength`, `maxlength`, `required`, `allowed`, `max-consecutive`) from the field attribute or an embedded per-site dataset (a small curated snapshot, MIT licensed from Apple's `password-manager-resources`), and make the generator satisfy them.
4. **Local vault** (`local/`, `backup/`), plan 03 *Local mode keys*: local unlock key = Argon2id(master password, local salt; 256 MiB where allowed, else 64 MiB) combined via HKDF with an optional 32-byte hardware secret supplied by the platform. Same ASK → vault key → item key hierarchy. A `LocalVault` that creates, unlocks, adds/edits/deletes items and serialises to one encrypted blob for the app to store. **Backup file** `.octapass-backup`: an authenticated header (magic `OPBK`, version, KDF params, salt) plus XChaCha20-Poly1305 over the serialized vault, keyed by Argon2id(256 MiB, t = 4) of the master password. A backup recovery code (same format as the account recovery code) that wraps the backup key. **Turn on sync** helper: produce what `register/finish` needs from an unlocked local vault, re-wrapping the ASK without decrypting items.
5. **WASM**: `importFile(source, bytes, options)`, `matchItems(url, overviews)`, `parsePasswordRules(text)` / `generateForRules(rules, options)`, `LocalVault` handle (create/unlock/export blob/backup/restore/upgradeToAccount). Document everything in `crates/octapass-wasm/README.md`.

## F. Server: batch writes, live sync, devices

1. `POST /v1/batch` → body `{ operations: [{ op: "put" | "delete" | "restore", vaultId, itemId, ifMatch?: number | "*", item?: { encryptedItemKey, overview, details } }] }` (max 1,000), atomic per vault, response `{ results: [{ itemId, status, revision? , problem? }] }`. Used by imports.
2. `GET /v1/ws`: a WebSocket. The first message from the client is `{ "type": "auth", "accessToken": "…" }`. The server then sends `{ "type": "vault-changed", "vaultId", "revision" }` for any vault the account can access, plus `{ "type": "account-deleted" }` and `{ "type": "session-revoked" }`. Never item data. Heartbeat ping every 30 s. Re-auth when the access token is refreshed, by sending a new `auth` message.
3. Devices: `GET /v1/devices` → `[{ id, name, platform, createdAt, lastSeenAt, current }]`, `PATCH /v1/devices/current { name }`, `DELETE /v1/devices/{id}` (remote sign-out: revokes that device's tokens and pushes `session-revoked`; deleting the current device is a sign-out).
4. **PostgreSQL** support behind `OCTAPASS_DATABASE_URL=postgres://…` with its own migrations directory, the same tests run against both (Postgres tests skip if no `OCTAPASS_TEST_POSTGRES_URL`). Stretch goal: do it last.
5. Keep the OpenAPI document and `docs/developers/sync-api.md` in sync. Integration tests for every new endpoint and the WebSocket.

## G. Autofill engine (`@octapass/autofill`)

A framework-free TypeScript library the extension's content script will use. It never sees the vault: it detects forms, asks a host callback for suggestions, renders the inline menu and fills values.

1. **Field and form classification**: login (username/email, current password), sign-up (new password, confirm password), change password (old/new/confirm), multi-step login (identifier first, password later), TOTP / one-time code (including split single-digit inputs), credit card (`cc-*` and heuristics), identity and address. Use `autocomplete` tokens first, then type, name/id/label/placeholder/aria in English plus the 10 most common languages incl. Arabic, then form structure. Score-based and explainable (`explain()` returns why a field got its type).
2. **Shadow DOM** and same-origin iframes. Cross-origin iframes are reported to the host (the extension decides).
3. **Inline menu**: a small icon in the field and a suggestion list rendered in a closed shadow root inside a top-layer popover, styled with the Octa Pass tokens (light/dark). Keyboard accessible. Items: matching logins, "Use suggested password" with preview (new-password fields), "Use a masked email" (email fields on sign-up forms, shown disabled with "Needs setup" for now), one-time code, cards, identities.
4. **Filling**: set values the way frameworks notice them (native setter + `input`/`change` events, React, Vue, Angular, Svelte), fill confirm fields, never fill hidden or zero-size fields, never fill without a user gesture, refuse when the target or our menu is covered or transparent (`IntersectionObserver` v2 where available plus `elementsFromPoint` checks).
5. **Save/update detection**: on submit, `fetch`/XHR completion and SPA navigation, report `{ url, username, password, formType }` to the host (it decides whether to prompt). Suggested password picked → report a draft immediately (plan 05).
6. **Tests**: unit tests with Vitest + jsdom, plus `tools/autofill-corpus/`: at least 40 synthetic, self-contained HTML pages (no real brands' code) covering classic login, email-first multi-step, sign-up with confirm, change password, React-controlled inputs, shadow DOM, same-origin iframe, split OTP boxes, card checkout, address form, Arabic RTL form, decoy hidden fields, clickjacking overlay, and a page that tries to restyle our menu. A Playwright runner (playwright-core with the system Chrome) loads each page, runs the engine and checks classification + fill results against expected JSON, reporting an accuracy score.

## History
- 2026-10-23: created (overnight build plan).
- 2026-10-24 (F, server): batch, WebSocket and devices built as specified, with these choices:
  - Batch `put` without `ifMatch` creates; with a revision it updates that revision; with `"*"` it updates whatever is stored (the item must exist). `delete` requires `ifMatch`. All changes to one vault share one new revision. Operations on a vault where another one failed answer `424` with the new problem type `batch-aborted`. Duplicate items, malformed ids or more than 1,000 operations reject the whole request with `400`. The batch body limit is 16 MiB (1 MiB elsewhere).
  - WebSocket: the server confirms each `auth` with `{ "type": "authenticated", "expiresIn" }` (an addition, so clients and tests know when they're subscribed) and closes with `4401` when the token expires without a re-auth, on bad tokens, revoked sessions and deleted accounts, and `4400` on protocol errors. A re-auth must be for the same device. `session-revoked` is also sent on logout and when a reused refresh token revokes the session. Notifications are in-process only: with several instances, a connection hears about writes made through its own instance.
  - Devices: `PATCH /v1/devices/current` answers `204`. The list only shows devices with a live session, and maintenance deletes device rows with no session left (signed out or expired). `lastSeenAt` updates on refresh and WebSocket auth.
- 2026-10-24 (F, server): fixed the findings of the independent security review of the merged server, each with a regression test:
  1. Verification-code brute force: one atomic `UPDATE … SET attempts = attempts + 1 … RETURNING code_hash` per guess; re-sending a code keeps the wrong guesses of an unexpired one; daily caps per email of 10 codes sent and 20 wrong guesses (`signup_counters`, keyed by an HMAC of the email, migration 0002); the per-email sign-up bucket now covers `register/finish`.
  2. Deleted accounts recoverable from disk: `PRAGMA secure_delete = ON` on every connection and `wal_checkpoint(TRUNCATE)` after each account deletion; the deletion test scans the raw `.db` and `.db-wal` files.
  3. Lockout and email flooding: separate buckets for failed logins per (email, IP) and a higher per-email ceiling, charged only by failed `login/finish` and `reauth/finish` and only peeked by the starts; `register/start` has its own per-email bucket plus the daily cap; email buckets are charged after validation.
  4. Pending-login outage: at most 20 in flight per IP, the oldest is evicted instead of refusing new logins, a 30 s TTL, and one IP token per request.
  5. Quotas: per-account limits on items (`OCTAPASS_MAX_ITEMS`, default 50,000) and item ciphertext (`OCTAPASS_MAX_ITEM_BYTES`, default 1 GiB) over the vaults it owns, trash included, tracked as running totals on `vaults` (migration 0003); writes that grow past them answer `403 quota-exceeded`. Sync is paged (about 1,000 items or 8 MiB) and never splits a revision: each vault's `revision` is the one the page is complete up to and `hasMore` says to sync again. **Workstream D:** `packages/vault-client` should loop while `hasMore` is true; clients that don't still store correct, partial revisions and catch up on the next sync.
  6. SMTP failures are logged as a kind and status code only, never the server's reply text, which can quote the recipient.
  - Also: the server's KDF ceiling now matches the client's (`t ≤ 16`, `p ≤ 4`, `m ≤ 1 GiB`).
- 2026-10-24 (F, server): PostgreSQL support through sqlx's `Any` driver, so every query is shared; `migrations/sqlite/` (the released files, moved unchanged so their checksums still match) and `migrations/postgres/` mirror each other. Other choices: archived items are imported with the tag `archived` (never dropped); 1PUX vault names become tags when the export has several vaults; 1PUX attachments and Bitwarden passkeys can't be used yet (passkeys keep every Bitwarden field in `extra`); Bitwarden's "exact" URI match maps to `startsWith`; values that aren't valid TOTP setups (Steam, HOTP) become hidden custom fields; generic CSV sniffs `,` `;` tab and has `previewCsv` + a `ColumnMapping` by header name; UTF-16 with a BOM is accepted, other non-UTF-8 is refused. The 10k-row fixture is generated by the test rather than committed; the encrypted Bitwarden fixtures are made by a Node script with Node's crypto, independently of the Rust code.
  - **URL matching:** per-URL modes live in a new optional overview field `urlMatch: { [url]: mode }` (keyed by the URL as written in `urls`; it round-trips today as an unknown field). **A/D: add it to the TS `ItemOverview` and the editor.** Qualities are `exact` > `domain` > `equivalent`. `startsWith` compares the parsed host and port and then a path-and-query prefix, never a raw string prefix (Bitwarden's string prefix lets `https://paypal.com` match `https://paypal.com.evil.io`). `regex` is unanchored over the full page URL with a 1 MiB compile limit. `schemeMismatch` is set whenever the saved URL's explicit scheme differs from the page's.
  - **Password rules:** Apple's dataset pinned at commit `91dff9a…` (436 sites, MIT, licence file next to it), looked up from the host up to its registrable domain. Rules from several sources combine by joining their text (repeated properties combine strictly), so WASM exposes `passwordRulesTextForSite(url)` next to `parsePasswordRules` and `generateForRules`.
  - **Local vault keys:** `pw_key = Argon2id(NFKD(password), local_salt)` (the salt is used directly; there's no email), `LUK = HKDF-SHA256(pw_key ‖ hw_secret?, salt = "", info = "openpass/v1/local-unlock")`; `hw_secret` must be 32 bytes. The core itself refuses an unbound vault whose password doesn't score 4 (`weak_master_password`), on create, password change and restore. The stored blob is JSON with the ASK-sealed body; items are kept as the same `EncryptedItem`s the server stores, plus Unix-ms timestamps and a trash (`deletedAt`). `changePassword` was added because restoring with the recovery code needs it anyway.
  - **Backups:** the backup key is derived (256 MiB, t = 4, random salt) when the vault is created or its password changes and kept inside the encrypted body, so automatic backups need no password; each file still gets a fresh nonce. The backup recovery code is stored in the body too, so the local Recovery Kit can be shown again while unlocked. Its wrapping key uses `info = "openpass/v1/backup-recovery"`, distinct from the account recovery key. The plaintext is `{ ask, vault }`, so a restored vault keeps its ids and item ciphertext. Test vector: `crates/octapass-core/tests/vectors/local-vault.json`.
  - **Turn on sync:** `vault.upgradeToAccount(email, password)` needs the email and an account password (the UI should prefill the local one) and uses the default account KDF; it returns an ordinary WASM `Signup`, so register/start → finish is the normal sign-up. The caller uploads `vault.items()` unchanged with `/v1/batch` `put`s (and `delete`s for items with `deletedAt`) and then deletes the local blob.
