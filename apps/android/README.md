# Octa Pass for Android

The native Android app ([plan 17](../../plans/17-native-mobile-apps.md)): Jetpack Compose with Material 3 and the brand tokens, edge to edge, with predictive back. Every screen is native; everything the vault does goes through `OctaPassVault`, the UniFFI API in [`crates/octapass-mobile`](../../crates/octapass-mobile/), so Kotlin does UI and platform services only. It replaced the Tauri phone app, which was removed on 2026-11-05 (plan 17).

## Layout

`apps/android` is one Gradle build:

| Path | What it is |
|---|---|
| `app` | The app (`app.octap.android`, minSdk 28). `ui/` holds the screens, `model/` the app's one `OctaPassVault` and what the screens watch, `platform/` the Android services the vault asks for or the screens use. |
| `wear` | The Wear OS app (Compose for Wear OS): shows the one-time codes the phone sends (`docs/features/watch.md`). It has the phone app's application id and signing key, as the data layer requires, and links no vault. |
| `vault` | The generated Kotlin bindings (`app.octap.vault`) and `jniLibs/` with `liboctapass_mobile.so`, built by `crates/octapass-mobile/scripts/build-android.sh`. Also its own JVM build for the binding tests. The app compiles its sources and packages its libraries. |
| `resources` | Strings (English and Arabic, plurals included) and design tokens generated by [`tools/native-resources`](../../tools/native-resources/). |
| `services/vault` | `app.octap.android.vault`: the Keystore-backed secrets, the device-unlock key and its prompt, the shared folder, the cached credential list. |
| `services/autofill` | The Autofill service and the Credential Manager provider, with credential transfer to and from other password managers. |
| `services/uitests` | The Autofill smoke tests' test app. |

The services moved here from the Tauri phone app unchanged in behaviour. They load the app's own library: `liboctapass_mobile.so` carries `octapass-ffi`'s UniFFI functions too (`Core.library`). The `octapass-ffi` bindings they use are in `core/`.

### How the screens are built

- **One activity** (`MainActivity`, `FLAG_SECURE` in release builds) and Compose throughout. `AppRoot` switches on the session: sign-in or sign-up, the lock screen, or the vault. Sign-up stays on screen through its Recovery Kit even once the account exists.
- **The vault** (`ui/vault/VaultHost`): a bottom bar on phones, a navigation rail on small tablets, the sidebar always beside the list on large ones (a drawer otherwise), and an item beside the list from 840dp. Screens are a Navigation 3 back stack (`VaultNavigator`), kept while the vault is locked so unlocking comes back to the same place.
- **Live data**: the vault's `VaultObserver` calls tick counters in `AppModel`; `rememberLive` runs a query again when items (or sharing) change.
- **Fonts**: Mona Sans (variable) and Monaspace Neon in `app/src/main/res/font`, converted from the web vault's files by [`tools/native-fonts`](../../tools/native-fonts/), with their OFL licenses in `assets/licenses`. `ui/theme/Theme.kt` sets them in the typography: headlines at the brand's 112% width.
- **Strings** come only from `resources` (`R.string.<group>_<key>`, the web vault's keys). Words only the native apps say are under `phone.native.*` in `apps/web/src/i18n/phone.ts`.
- **Platform services**: `AndroidPlatform` (Keystore, `BiometricPrompt` with `BIOMETRIC_STRONG or DEVICE_CREDENTIAL`, the credential list), the clipboard that clears after 30 seconds, the system pickers and viewer through the app's `FileProvider`, Wi-Fi Connect (`ACTION_WIFI_ADD_NETWORKS`), CameraX with ZXing for QR codes, the print framework for the Recovery Kit.
- Other apps' autofill services never see the app's fields (`IMPORTANT_FOR_AUTOFILL_NO_EXCLUDE_DESCENDANTS`).

Debug builds are `app.octap.android.native`, so they install next to a release build; release builds are `app.octap.android`, the id the Tauri app had, so they take over its data.

## Build and run

On a Mac with Java 17, the Android SDK and NDK, and the Rust Android targets:

```sh
crates/octapass-mobile/scripts/build-android.sh      # the library and bindings (or only x86_64 for an Intel emulator)

# A local sync server; the emulator reaches it through adb reverse.
OCTAPASS_BIND='[::]:8097' OCTAPASS_DEV_MODE=true OCTAPASS_RATE_LIMITS=off OCTAPASS_DATA_DIR=/tmp/octapass-dev cargo run -p octapass-server
adb reverse tcp:8097 tcp:8097

cd apps/android
./gradlew :app:installDebug -PoctapassServer=http://localhost:8097
```

`-PoctapassServer` points the "Octa Pass" server choice at the local server (the default is the hosted one).

From the repository root, `pnpm dev:android` does the same in one step, and rebuilds the library whenever its Rust sources changed since the last build. It installs on the only emulator or phone `adb` lists, or asks which one, and uses whichever of `pnpm dev:api` and `pnpm start` runs on the computer, through `adb reverse`. `pnpm dev:android --setup` asks both questions, and `ANDROID_SERIAL` or `OCTAPASS_SERVER_URL` skip them.

## Test

`screenshots/` holds the main screens in both themes and languages, from `ScreenshotsTest`.

```sh
cd apps/android
./gradlew :app:testDebugUnitTest :octapass-vault:testDebugUnitTest :octapass-autofill:testDebugUnitTest
./gradlew :app:connectedDebugAndroidTest -PoctapassServer=http://localhost:8097   # an emulator with the screen-lock PIN 1111
```

The Compose UI tests drive the real screens against the development server, which shows its email codes: sign-up with the Recovery Kit, unlock, two-step sign-in with either method, device unlock with the screen lock, the list's menu, website rows and search, favourites and the trash, the editor, the generator, Health, QR codes, settings in Arabic, two-step settings, share links, families and shared vaults. They use Compose's v2 test rule: with the v1 rule's unconfined dispatcher, a vault call resumes inside the Rust thread's callback, which JNA can't nest on Android.
