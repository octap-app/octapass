## I. Passkey authenticator (core)

A software WebAuthn authenticator in `octapass-core`, so passkeys are ordinary encrypted items (plan 05 *Passkeys*).
- **Create:** given `rpId`, `userHandle`, `userName`, `challenge`, `origin`, allowed algorithms → generate an ES256 (P-256) key (EdDSA when the RP lists it first), credential ID = 16 random bytes, `authenticatorData` (rpIdHash, flags UP|UV|BE|BS|AT, signCount 0, AAGUID = the Octa Pass AAGUID constant), attestation `none` in CBOR, `clientDataJSON` built from the caller's values. Returns the public credential JSON (WebAuthn Level 3 `toJSON` shape) and the passkey record to store in the item (`rpId`, `credentialId`, `userHandle`, `userName`, private key PKCS#8, `createdAt`, `signCount`).
- **Get:** given `rpId`, `challenge`, `origin`, `allowCredentials` → select matching passkeys (the host passes candidates), sign `authenticatorData ‖ SHA-256(clientDataJSON)`, return the assertion JSON. Sign counter stays 0 (synced passkeys).
- **Origin checks** in the core: `rpId` must equal the origin's host or a registrable-domain suffix of it (use the matching module's PSL), the origin must be `https` (or `http://localhost`), and cross-origin iframes are refused unless the host says the frame is allowed.
- **Tests:** verify signatures with an independent verifier (the `webauthn-rs` or `passkey` crates in dev-dependencies, or `p256` verification), test vectors, and the FIDO `none` attestation format. The private key never leaves the core unencrypted except inside the item's encrypted details.
- **CXF (stretch):** export/import passkeys in the FIDO Credential Exchange Format JSON.

## J. Desktop app (Tauri 2)

- `apps/desktop`: a Tauri 2 app for macOS, Windows and Linux. The UI is the web vault (`apps/web`) built with a `TauriVaultService` (`VaultService` over Tauri commands). The Rust side links `octapass-core` directly, so keys live in native memory, not in the webview.
- Native unlock on macOS: Touch ID / Apple Watch **or the Mac login password**, via `LocalAuthentication` (`deviceOwnerAuthentication`) and a Keychain item protected by `SecAccessControl` (`.biometryCurrentSet` or `.devicePasscode`; plan 03). Windows Hello and Linux polkit behind the same trait, compiled only on those targets.
- **Fill without unlocking** (plan 03) behind the same trait, only offered when the OS reports no device lock.
- A **quick-access window** on a global shortcut (Cmd/Ctrl+Shift+Space): search, copy username/password/code with clipboard auto-clear. Auto-type is a later milestone.
- **Native messaging host** binary (`octapass-native-host`) and manifests for Chrome, Edge and Firefox, so the extension can unlock through the desktop app (protocol: length-prefixed JSON, requests `unlock-status`, `unlock`, `get-session-key-wrap`; only the extension IDs in the manifest may connect).
- Tests: Rust unit tests for the commands and the unlock trait (with a fake platform), a `cargo tauri build --debug` that produces a runnable `.app`, and screenshots of the running app.

## H. Browser extension (MV3)

- `apps/extension`: Chrome/Edge (MV3 service worker) and Firefox (MV3 with background scripts) builds from one Vite config. CSP allows `wasm-unsafe-eval` for the core.
- **Service worker** hosts the milestone 1 remote vault service (no `window`), keeps the unlocked session wrapped in `chrome.storage.session`, auto-locks, and uses `@octapass/core` for matching, generator, TOTP and passkeys.
- **App page** reuses the web vault's React screens (shared components move into `packages/ui`; coordinate that refactor in History). Built first as a popup and side panel; since 2026-11-07 the toolbar button opens it in a tab instead (History 2026-11-07, plan 05).
- **Content script** runs `@octapass/autofill`: inline menu suggestions from the service worker's exact-domain matches, suggested strong passwords with immediate draft save, save/update prompts, TOTP fill, cards and identities.
- **Passkeys:** a MAIN-world script wraps `navigator.credentials.create/get`. When the user picks Octa Pass, the core authenticator (I) answers. Otherwise it falls back to the browser.
- **Unlock:** master password, device unlock through a passkey PRF (as in the web vault; not built in the extension yet, see History 2026-10-24 Firefox Touch ID; Firefox can't make one for the extension at all, History 2026-11-04), or the desktop app over native messaging.
- **Local mode** (plan 01 *Local mode*): "Use on this device only" with the core `LocalVault` (E), encrypted backups, Turn on sync.
- Tests: unit tests, and Playwright with the Playwright Chromium build (`--load-extension`) running the extension against the autofill corpus and a local server: sign in, fill a login, save a new login from a sign-up page with a suggested password, create and use a passkey on a local WebAuthn test page.

- 2026-10-24 (Q, bridge hardening, branch `m3-bridge-hardening`): fixes the security review's finding that `bridge.rs` trusted `Forwarded.origin`, a string the socket client supplies. Any same-user process could connect to `native-host.sock`, or start the genuine host with a forged origin argument, and ask for `get-session-key-wrap`.
  - **Design:** the checks live in `octapass-native-host` (`trust.rs`), so the host and the app share them. They read processes through a small `System` trait (executable, parent, signature, root ownership, system shell), which tests replace with fakes. `system/{macos,linux,windows}.rs` are the real implementations. `browsers.rs` holds the per-OS table of known browsers.
  - **App side:**
    - The app gets the peer from the OS: on macOS the `LOCAL_PEERTOKEN` audit token (PID = word 5), on Linux `SO_PEERCRED`, on Windows `GetNamedPipeClientProcessId`.
    - The peer's executable (`proc_pidpath`, `/proc/<pid>/exe`, `QueryFullProcessImageNameW`, canonicalised) must equal the canonical `octapass-native-host` next to the app's executable.
    - macOS release builds also require the host's code to meet `anchor apple generic and certificate leaf[subject.OU] = "<the app's own team>"`. The team comes from `SecCodeCopySelf`, and the check runs on the `SecCode` that `SecCodeCopyGuestWithAttributes` returns for the audit token, whose main executable must be that same path. Debug builds, and release builds with no team (ad hoc), skip the signature check and log it at startup.

The application identifier also opens the data protection keychain to device unlock; `macos/system.rs` already falls back to the login keychain when reading, so keys saved before keep working. **Tests:** `src/entitlements.test.ts` (template alone, the app group, the three entitlements only with the profile, refusals); the desktop's Vitest suite (53). **Not verified:** nothing on a Mac: Xcode's automatic profile for the stand-in, Tauri embedding it and signing the app with it, the app starting, and above all whether this is what System Settings wants. It's the remaining difference from the iPhone, not a documented requirement.
