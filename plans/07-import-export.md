# 07 — Import and export

Imports run entirely on the device. Files are parsed by `octapass-core::import`, previewed, then encrypted and uploaded in batches. The plaintext file is never sent to the server.

## Import flow (UX)

1. Pick the source, with a short per-source guide (screenshots in the docs) on how to export from that app.
2. Drop the file. Parsing happens on the device and shows counts per item type plus warnings (unsupported fields go into custom fields or notes, never dropped).
3. Choose the target vault. Items already there are matched and updated, never copied (`import/reimport.rs`, History 2026-11-04). Option: *tag imported items* (`import-2026-10-22`).
4. Encrypt and upload with a progress bar. It's resumable if interrupted.
5. Remind the user to **delete the export file**, since it's plaintext on disk. On desktop, offer to securely delete it.

## Export

| Format | Contents | Use |
|---|---|---|
| **Octa Pass encrypted export** (`.octapass`) | Everything, including attachments in a ZIP; encrypted with an export password (Argon2id + XChaCha20-Poly1305) | Backups, moving between Octa Pass accounts |
| **Octa Pass JSON (plaintext)** | Everything | Scripting. Strong warning in the UI. |
| **CSV** | Logins only (Chrome-compatible columns + `totp`, `notes`) | Moving to any other manager |
| **CXF** | Passwords, passkeys, TOTP, notes, cards, identities | Moving to another CXF-capable manager |

- Export needs the master password again (not just biometrics).
- It's logged in the account security log ("Vault exported on device X").
- Organisations (P2) can disable plaintext export by policy.

## Testing

- `tools/import-fixtures/`: synthetic export files for every format and version (no real data), including edge cases: Unicode, RTL text, multiline notes, quotes/newlines in CSV, huge files (50k items), malformed rows.
- Every parser is fuzzed (`cargo fuzz`).
- Round-trip tests: Octa Pass JSON → import → export is identical. CXF round-trips with other implementations' published test vectors.

## History
- 2026-10-24 (branch `m9-export`): import and export completed. Decisions:
  - **Encrypted export file** (`crates/octapass-core/src/export/archive.rs`): header `OPEX` ‖ version ‖ Argon2id m/t/p ‖ 16-byte salt ‖ 19-byte nonce prefix, then XChaCha20-Poly1305 in 64 KiB STREAM chunks (the attachments' construction, now shared in `stream.rs`) with the whole header as associated data. Key = HKDF-SHA256(Argon2id(NFKD(password), salt), info `openpass/v1/export`). Argon2id defaults to 256 MiB, t = 3; files are read with `KdfParams::validate`, so a crafted header can't weaken or freeze anything. A wrong password fails on the first chunk; damage or truncation anywhere fails. The plaintext is a standard ZIP (always ZIP64 records, so size limits need no second path) with `export.json` (the plaintext JSON format, attachment keys removed) first and `files/<attachment id>` after; any unzip tool opens it once decrypted. Writer and reader both stream: one attachment's plaintext in memory at a time, and the reader returns the items before the files so they're saved first. The export password must be at least 10 characters in the apps.
  - **Import of Octa Pass exports** goes into the chosen vault of any account (or a local vault) with new ids and keys. Recovery info linked to an imported Identity is re-pointed at its new id (`import::relink`). Files are re-encrypted and uploaded after their items; a local vault (extension, no account) keeps the items and reports the files it can't hold. The plaintext JSON imports without files, with a warning.
  - **CXF** (`export/cxf.rs`, `import/cxf.rs`) follows CXF 1.0 (Proposed Standard, errata 2026-03-09) as a JSON file; the Credential Exchange Protocol isn't done. Export: one account, vaults as collections when there are several, `exporterRpId` = the server's host. Import accepts a `Header` or a bare `Account` (what Dashlane and 1Password write), maps every credential type, splits a login and a card in one item into two items, and reports files and unknown types. Password history, recovery info and files have no CXF field and are left out with a warning. Tested against the spec's Appendix A example and Dashlane and 1Password exports from Bitwarden's SDK test resources (GPL-3.0, cited in the fixtures README).

Authenticator backups added `aes-gcm` and `scrypt` (+94 KB). Done later in `m21-importers`: Bitwarden CSV, Raivo, Ente Auth encrypted and Proton's PGP-encrypted export. Not done: Dashlane's `.dash` archive (its format isn't documented) and attachments from other apps.

- 2026-10-24 (branch `m14-import-fidelity`, maintainer feedback: a Firefox CSV kept only url/username/password): every importer maps each field its app exports to its meaning. Decisions:
  - **Item model, additive** (no schema version change; older clients keep unknown fields): `ItemOverview` gained `createdAt`, `updatedAt`, `lastUsedAt` and `importedFrom { source, id }`; `LoginDetails` gained `passwordChangedAt` and `httpRealm`. They live inside the encrypted overview and details, so the server keeps only its own sync timestamps and the source dates survive sync. Apps show `overview.createdAt ?? record.createdAt`, `overview.updatedAt ?? record.updatedAt`, `lastUsedAt`, and "Password changed" as the later of `passwordChangedAt` and the newest history entry (`itemDates` in vault-client). An edit that doesn't set a new `updatedAt` drops the imported one (`withPasswordHistory` in TypeScript, `with_password_history` in the desktop and phone vaults, `update_login` in the FFI), so "Last changed" becomes the edit's date.
  - **Re-import** (`import/reimport.rs`): `ImportOptions` takes `existingItems` (the target vault's items) and `now`; `ImportResult` gets `updates` (item id + merged item) and `unchanged`. Matching: same `importedFrom` source and id (and the same kind of item), else a duplicate key: login origin + username (or title when both are empty), card number, identity title + name + contacts + first address line, note title + text. Another item with the same app but a different id is never a duplicate. The merge takes the file's values for the fields it has and keeps the rest; URLs, tags, custom fields (by label), passkeys and password history are unions; attachments always stay; a replaced password goes into the history dated `passwordChangedAt`, else the file's `updatedAt`, else `now`. Identical results count as unchanged and aren't written. The clients save updates through their normal edit path, which doesn't add the old password again when the draft already did. Octa Pass exports and authenticator backups aren't reconciled: their items stay new, and an Octa Pass export → import → export round trip stays identical.
  - **Dates** are normalised to RFC 3339 UTC (`build::timestamp`/`unix_time`: Unix s or ms told apart by size, ISO 8601 with offsets, bare dates); anything before 1990 counts as "not recorded".
  - **Per source:** Firefox `guid`/`timeCreated`/`timePasswordChanged`/`timeLastUsed`/`httpRealm` (no longer a custom field); Bitwarden `id`/`creationDate`/`revisionDate`/`login.passwordRevisionDate`; 1PUX `uuid`/`createdAt`/`updatedAt`; Proton `itemId`/`createTime`/`modifyTime` (+ `lastUseTime` where present) and the CSV's dates; Enpass `uuid`/`createdAt`/`updated_at`/`last_used` and the password field's `value_updated_at`; Dashlane JSON `id`/`creationDatetime`/`userModificationDatetime`/`lastUse`; Keeper Commander `$record_uid`/`uid`/`last_modified` (the Web Vault's per-export integer uids aren't kept); KeePass `UUID`, `Times`, auto-type default sequence and windows (→ `autoType`), KeePassXC `KPEX_PASSKEY_*` (→ passkeys that can sign in), KeePassXC CSV dates; CXF `id`/`creationAt`/`modifiedAt` (and the CXF export now writes an item's imported dates). Generic CSV reads known apps' headers with their own importer, splits Bitwarden CSV `fields`, and recognises date and id columns. Each `docs/import-export/from-*.md` page has a field table; mappings we couldn't confirm in an app's own docs are marked as best guesses there.

- 2026-11-04 (maintainer report: importing items that already exist made copies): **Octa Pass exports are reconciled too**, which reverses the 2026-10-24 decision that kept their items new. Restoring a backup into the vault it came from doubled every item, and an export holds every vault while an import goes into one, so a family vault's items were copied into Personal. Decisions:
  - **Match by the item's own id first, in every vault.** Clients now pass every vault's live items with `vaultId` and `updatedAt` (`ExistingItem`), and the target in `ImportOptions::vault_id`. Other imports still compare only the target vault's items; an Octa Pass export also finds its own ids anywhere. When no id matches, the usual duplicate key applies, in the target vault only, so importing one export into another account twice is recognised the second time. Ids are matched for every item before any duplicate is, so a deleted item can't take its look-alike's place.
  - **The newer version wins**, by the export's `updatedAt` against the vault record's, in UTC and to the sub-second (records keep milliseconds, and an edit right after an export must count as newer). An item changed in the vault after the export stays as it is (counted as unchanged, with one warning saying how many); restoring an old backup to get back one deleted item must not roll back every password changed since. When the export is newer, its item replaces the vault's whole (no unions, unlike other apps' files: an Octa Pass item is complete), keeping the vault's attachments and password history, with the vault's password added to it.
  - **Links and files follow the matches.** Recovery links to a matched item point at the vault's id (`relink` inside the core); clients relink updated items too (`import::relink_all`), since an update can point at an item the import brings back. An encrypted export's files go to matched items that have neither that attachment id nor a file with the same name and size (`ImportResult::existing_files`, attached like `files`), and not to items the vault's newer version kept. The plaintext export's "files aren't in this export" warning counts only files that would have been brought back.
  - The WASM `ExportReader` takes the same options as `importFile`.
  - **More duplicate keys:** documents (title + notes), SSH keys (the public key's type and base64, else the fingerprint), keys (public key, else fingerprint; a secret-only key has nothing safe to compare and stays new), certificates (the PEM without whitespace), environments (project + stage, else the title). Keys, certificates and fingerprints compare exactly, not lowercased. Password-only items still match by title alone: merging two different items is worse than one extra copy. The vault's duplicate keys are worked out once per import rather than once per imported item.
  - **Adding a login by hand** asks when one for the same site and username exists (`packages/vault-client/src/duplicates.ts`, the importer's rule; a login without a website isn't compared): keep editing, open the one you have, or save a copy. Opening it still asks about the unsaved changes, because the new password may be the one to keep. The phone apps ask through `OctaPassVault.sameLogin` (`crates/octapass-mobile`, the same rule in Rust) and offer keep editing or save a copy only (plan 17a).

Decisions:
  - **The rule:** two URLs are the same website when autofill would offer the login on the same pages, read with the match mode of the one that stays (the earlier one). `subdomains` (the default since the same day, plan 05 History, also for a URL without a mode) and `baseDomain`: the same host ignoring case, a leading `www.`, scheme, port, path, query and fragment. Under `subdomains` that is exactly the same pages, since `www.` counts as the bare host there. Hosts, not registrable domains: under `baseDomain` `a.example.com` and `b.example.com` fill on the same pages, but people keep both on purpose and the item shows two hosts. `host`: the same host and effective port, as the matcher compares them (so `http://` and `https://` differ, `www.` counts). `startsWith` and `never`: the same URL after WHATWG serialisation only (lower-case scheme and host, default port dropped, `/` for an empty path; a trailing slash after a path counts, since `/admin` also starts `/administrator`). `regex` on either side, an unknown mode, or something that isn't an `http(s)` address: the same trimmed text. There is no `exact` mode (Bitwarden's maps to `startsWith`).
  - **The first stays, with its mode.** A later URL without a mode joins an earlier one that has one, so a re-import from Chrome can't undo a `host` rule the user set. Dropped URLs take their `urlMatch` entries with them.
  - **Import merge:** the vault's URLs first, then the file's, deduplicated (before, the file's came first). `urlMatch` is merged with the file's modes on top for the same text, as for any field, then cut to the URLs that stay. Each imported item is also deduplicated on its own (`import_file`, every source). RoboForm's `MatchUrl` is now dropped when it's the same website as `Url`.
  - **Everywhere else:** the item view shows each website once (web `LoginFields`, iOS `ItemDetailView`, Android `ItemScreen`; the phones call `uniqueWebsites` in `crates/octapass-mobile`, so the rule isn't written in Swift or Kotlin). Saving through the editor drops repeats (web `cleanDraft`, `octapass-mobile` `draft_json`). The phones' AutoFill save (`octapass-ffi` `update_login`) adds a page's address only when the login has no same website. The extension's "update this login" only changes the password, so it needed nothing. No migration: stored repeats stay until the item is saved or merged by an import.

- 2026-11-08 (maintainer report: an exported JSON, CXF and encrypted file "not able to import in the same Octa Pass", and the CSV import turned Wi-Fi networks into secure notes): **our own exports import back as they were.**
  - **JSON and encrypted** already round-tripped. Imported into the same account, even into a new, empty vault, every item matched its own id in the vault it was already in (the rule above: an export holds every vault, so ids match in any of them), nothing was added to the chosen vault, and the result was `0 new, 0 updated, N unchanged`, which read as a failure. That matching is unchanged; copying an export's items into another vault of the same account isn't something an import does yet. The web import now says "All N items are already in your vaults, so nothing was added." (`import.alreadyThere`).
  - **Own CSV** (`import/own_csv.rs`): the generic CSV importer recognises the exact header `exportCsv` writes (`vault,type,title,url,username,password,totp,notes,tags,favorite`) before the other apps' headers, and rebuilds each row by its `type`. Wi-Fi (SSID, security, hidden, EAP method, phase 2, identity, server domain, sign-in page, managed, hotspot), card, identity and the field-table types (bank account, licence, ID document, database, wallet) read their known `Label: value` lines from the top of the notes; logins and Wi-Fi read the remaining leading `Label: value` lines as custom fields (hidden when the label sounds secret), which is how the export writes them. Reading stops at the first other line, so the user's own notes stay as written. `vault` is ignored (the import goes into the chosen vault). Types a CSV can't hold (SSH keys, documents, certificates, keys, environments, API credentials, custom items) become notes with every line kept, with one warning. Before, every row went through the generic login builder: a login, or a secure note without a website, plus `vault` and `type` as custom fields.
  - **CXF Wi-Fi** (`import/cxf.rs` `add_wifi`): a `wifi` credential becomes a Wi-Fi item (it was a note of `Network:`/`Password:` lines). `networkSecurityType` maps back to the item's security; the custom fields our export writes for what CXF lacks (`Security` for Enterprise and other types, EAP method, phase 2, username, identity, server domain, CA certificate) go back to their fields, and other custom fields stay custom fields.
  - **Re-import merge** (`reimport.rs` `same_address`): an identity's `address` from the file is skipped when it reads the same as the vault's as one line, so a CSV's flattened address doesn't replace the vault's postcode, city and region.
  - **Not changed:** CSV and CXF still match only in the target vault, so items from other vaults come in as new; CXF still adds the vault name as a tag (collections are tags). The JSON or encrypted export is the one for backups.
  - **Open Pass files:** Open Pass, the project this is a fork of, writes the same documents with `"format": "openpass-export"` and the `.openpass` extension (the encrypted file is the same `OPEX` archive). `ExportDocument::parse` and the TS `parseOctaPass` accept both names, and the web import's file picker offers `.openpass`. Open Pass does the same the other way round. Exports still write `octapass-export`.
