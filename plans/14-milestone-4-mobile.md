# 14 — Milestone 4: iPhone and Android apps (build contract)

Builds on milestones 1–3. Same rules as plans 11–13. Mobile UI is Tauri 2 mobile with the shared React screens (plan 02, with React Native as the fallback if Tauri mobile blocks the autofill extensions). The autofill and passkey providers are native (Swift / Kotlin) and call the Rust core through UniFFI.

## Workstreams

| Workstream | Branch | Owns |
|---|---|---|
| **K. Mobile core bindings** | `m4-ffi` | `crates/octapass-ffi/**` (UniFFI: session, items, matching, TOTP, passkeys, device unlock), generated Swift/Kotlin packages under `apps/mobile/bindings/**` |
| **L. iOS app** | `m4-ios` | `apps/mobile/ios/**` plus the Tauri mobile shell under `apps/mobile/**` (shared with M, coordinate in History) |
| **M. Android app** | `m4-android` | `apps/mobile/android/**` |

## K. UniFFI bindings
- `octapass-ffi` exposes a small, safe API over `octapass-core` and a minimal HTTP client trait implemented natively (URLSession / OkHttp), so the autofill extensions can unlock and read the encrypted local store without the full app.
- Builds an XCFramework (iOS device + simulator) and Android `.so` libraries (arm64-v8a, x86_64) with the NDK. Swift and Kotlin unit tests call the bindings.

## L. iOS
- Tauri 2 iOS app with the shared screens. Device unlock: Face ID / Touch ID **or the device passcode** (Keychain item with `[.biometryCurrentSet, .or, .devicePasscode]`; plan 03).
- **AutoFill Credential Provider extension** (Swift): passwords, passkeys (`ASPasskeyCredentialRequest`, iOS 17+) and one-time codes (iOS 18+); registers identities with `ASCredentialIdentityStore`. Shares the encrypted store through an App Group, under the extension memory limit.
- **Wi-Fi Connect** button (`NEHotspotConfiguration`) and QR display/scan (plan 01 *QR codes*).
- Test on the iOS Simulator (`xcrun simctl`): build, install, launch, screenshot the main screens and the AutoFill extension list.

## M. Android
- Tauri 2 Android app with the shared screens. Device unlock: `BiometricPrompt` with `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`.
- **AutofillService** (inline suggestions on Android 11+, "Suggested password" dataset for new-password fields) and a **CredentialProviderService** for passkeys and passwords (Android 14+).
- **Wi-Fi Connect** (`WifiNetworkSuggestion` / `ACTION_WIFI_ADD_NETWORKS`) and QR display/scan.
- Test on an emulator (install a system image with `sdkmanager` if missing), with screenshots.

Decisions L and M should know:
  - One error type: `OctaPassError` / `OctaPassException`, typed cases plus `Core { code, reason }`. Error fields are never named `message`, because that clashes with Kotlin's `Throwable.message`.
  - HTTP goes through a synchronous native `HttpClient.send` (call into the core off the main thread). `OctaPassServer` reuses the `octapass-api` types and also does sync, logout, account deletion and uploads of local changes. Conflicts become "<title> (conflicting copy)" items, as in the web vault. Tokens, the Secret Key and the device secret stay in the app's Keychain / Keystore storage.
  - `LocalStore` is the shared file for the app and its extensions. It's a binary file (`OPLS` v1, raw ciphertext and ids, SHA-256 trailer, layout in the crate README) holding only what the server holds, plus the device-unlock record. Writers lock `<file>.lock`, re-read, then replace the file atomically, so the app and an extension never lose each other's writes. No new cryptography: every secret is a core envelope.
  - Device unlock wraps the ASK with the core's device-unlock derivation, using a 32-byte secret the app keeps behind the device lock (Keychain `[.biometryCurrentSet, .or, .devicePasscode]`, or a Keystore key with `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`). The FFI enforces the 14-day master password rule (`PasswordRequired`).
  - Passkeys: `ClientData::Web` uses the core flow. `Json` (Android apps, after the provider checked Digital Asset Links) and `Hash` (iOS, and Android browsers that pass `clientDataHash`) sign the platform's client data. That signing lives in the FFI for now (TODO(core): a hash-taking `get` in `octapass_core::passkey`). Created passkeys are saved to the store before the credential is returned. `passkeyCreationRequestFromJson` / `passkeyAssertionRequestFromJson` read Credential Manager's `requestJson`.
  - Matching uses `octapass_core::matching` (merged from `m1-integration`) for websites, with each item's `urlMatch` modes and the default equivalent domains; `MatchQuality` has `Exact`, `Domain` and `Equivalent`. Only `androidapp://<package>` exact matching lives in the FFI, because the core matcher is web-only. Sync follows the server's paged responses (`hasMore`).

- 2026-10-24 (attachments, `m8-mobile-attachments`): the phone apps add, open and remove files, offline too. Mirrors the desktop crate (`octapass_core::attachment`, per-file keys wrapped by the item key, 64 KiB chunks), adapted to the phone saving first and uploading later. Decisions:
  - **Plaintext never passes through the web view.** Android's Tauri IPC is JSON over `postMessage` (no raw bodies), and a 100 MB file shouldn't be copied through JavaScript anyway, so the phones use their own pickers and viewer from Rust: `Native` gained `file_sources`, `pick_files(source, into)` (the system pickers copy into a new folder in the app's private temp storage and return paths) and `open_file(path, name, type)` (returns when the viewer is closed). The web view only gets `PickedFile` descriptions and calls `attach_picked`, `discard_picked` and `open_attachment` (plan 11's `NativeFiles`). Picked and decrypted files live in `Config.temp_dir` (iOS `NSTemporaryDirectory`, Android `cacheDir`; never the App Group), are deleted after use, and the whole folder is emptied on lock, sign-out and start.

  - **Android:** `ACTION_OPEN_DOCUMENT`, the system photo picker (`PickMultipleVisualMedia`, no storage permission), `ACTION_IMAGE_CAPTURE` writing straight to a `FileProvider` URI after the CAMERA runtime permission (Tauri's `@Permission` alias); `ACTION_VIEW` with a read-only content URI named after the file, falling back to the share sheet, else `noFileViewer`. It reuses the generated app's `${applicationId}.fileprovider` (cache root). The photo picker hides real names, so photos get names like `21.png`.
  - **The outbox** (`crates/vault/src/outbox.rs`, `<tag>.files/` next to the store): a new file is encrypted straight into `<attachmentId>.upload` (ciphertext exactly as uploaded) and queued in `changes.json` (ids only) before it's listed in the item, which is saved locally like any edit; removals queue a delete (or just drop an upload that never went up). `push_changes` runs on every save, sync and attachment call: files for items the server already has go first, so a list never names a missing file; then the items (`upload_pending`), which creates new items before their files ("item before its files"); then the remaining files and the deletions. Retries are the next push (unlock, save, foreground). `already-exists` counts as sent; `not-found` waits; a file the server refuses for good (too large, over quota, not an attachment) is taken off its item with a `SyncFailed` event. Changes stay until the item's list is uploaded too. Files waiting to upload are marked `pending` in what the UI gets, and open from the outbox, offline too. Online, sizes and the owner's quota (counting queued bytes) are checked before encrypting, as on the desktop. Large transfers use per-request timeouts (1 hour, 1 minute without progress) instead of the 30-second default, upload from the file on disk and decrypt the download as it streams; nothing reaches the viewer before the whole file verified.
  - **Conflicts (FFI change):** `OctaPassServer::upload_pending_resolving` (Rust-only, `app.rs`) lets the caller settle a conflict with a `Resolution { merged, copy }`; `merged` is saved over the server's version and uploaded once more in the same push. The exported `upload_pending` keeps its behaviour except that conflicting copies leave out `attachments` (their keys are bound to the original item, as the desktop and web already do). The mobile vault's resolver puts this phone's file changes on top of the server's version and makes a copy only of other edits: it keeps the item's record from before its first file change (`bases.json`, ciphertext as stored) to tell them apart. Also Rust-only: `Session::new_attachment`, `open_attachment` and `decrypt_record` on stored items (an item not uploaded yet has its key in the store). Exported API and bindings unchanged.

  - **Signing without committing a team.** `cargo tauri ios build` puts `APPLE_DEVELOPMENT_TEAM` on the app target only and doesn't pass the variable to `xcodebuild`, so the AutoFill extension failed ("Signing for OctaPassAutoFill requires a development team"). The project's base configuration is now `gen/apple/Signing.xcconfig`, which includes the gitignored `Signing.local.xcconfig` (`DEVELOPMENT_TEAM = …`); every target inherits it. `scripts/ios-device.sh` writes that file from `APPLE_DEVELOPMENT_TEAM` (or the gitignored `ios-device.env`), builds with `--export-method debugging`, puts back the `project.pbxproj` Tauri edits, and installs and launches with `xcrun devicectl`.
  - **Set Up Codes In.** Apple lists the apps that handle `otpauth://` there ([Apple staff, developer forums](https://developer.apple.com/forums/thread/780204)); `ProvidesOneTimeCodes` (already set) is the separate AutoFill side ([Providing one-time passcodes to AutoFill](https://developer.apple.com/documentation/authenticationservices/providing-one-time-passcodes-to-autofill)). The app declares `otpauth` and `otpauth-migration` in `CFBundleURLTypes`. Opened URLs arrive as `RunEvent::Opened` (cold starts too, through the scene's connection options); `src-tauri/src/links.rs` keeps those two schemes (up to 8 KiB), queues them and emits `app://opened-links`; the web view takes them with `take_opened_links` once unlocked. **Any website can open such a link, so nothing is saved until the user taps Add**; then the vault's `otpauth` importer adds it, joining the login with the same issuer or making a new one. When `m10-qr-totp` merges, `OpenedLinks` should hand the links to its `ScanCodesDialog` (`initialTexts`) for the link-to-login picker instead of importing directly.
  - **Turning AutoFill on.** Native calls `autofill_status`, `turn_on_autofill`, `open_code_settings` (iOS) and `open_passkey_settings` (Android). iOS: `ASCredentialIdentityStore.getState`, [`ASSettingsHelper`](https://developer.apple.com/documentation/authenticationservices/assettingshelper) `requestToTurnOnCredentialProviderExtension` on iOS 18 (asks in place; one request per 10 s), else `openCredentialProviderAppSettings`, and `openVerificationCodeAppSettings` for Set Up Codes In; Octa Pass's own Settings page as the fallback. Android: `AutofillManager.hasEnabledAutofillServices` and `ACTION_REQUEST_SET_AUTOFILL_SERVICE`; on 14+ `CredentialManager.isEnabledCredentialProviderService` and `Settings.ACTION_CREDENTIAL_PROVIDER`. Shown as **Settings → AutoFill** (through a new `platformSection` slot on the web `SettingsPage`) and as a dismissible prompt on the item list while AutoFill is off.

- 2026-10-24 (mobile polish, `m10-mobile-polish`): on a real iPhone the app felt like a web page (pinch zoom, zoom into fields, rubber band, grey taps, sticky hover). Until the native apps of plan 17, the Tauri apps now behave natively. Details in `apps/mobile/README.md` ("Feeling native"). Decisions:
  - **No page zoom; text size through CSS.** Viewport `maximum-scale=1, user-scalable=no`; iOS turns off the scroll view's pinch and fixes zoom at 1, Android turns off WebView zoom and keeps its text zoom at 100%. The plugin's `text_scale` (Dynamic Type body size / 17, Android `fontScale`) sets the root font size, clamped to 80–160% because larger no longer fits the screens; it's read again whenever the app comes back.
  - **Fields ≥ 16px on touch screens** through a shared token, `--field-min` (0 by default, 16px under `pointer: coarse`), used by `TextField`, `Select`, the base field rule and the two larger fields. The web vault on phone browsers gets it too; desktop is unchanged.
  - **Hover only with a pointer:** a PostCSS step in the app's build (`config/hoverOnly.ts`) wraps every `:hover` rule in `@media (hover: hover)`, rather than editing 29 web rules; mobile.css adds press states.
  - **Keyboard:** the web view ends at the keyboard (iOS `keyboardLayoutGuide` with `usesBottomSafeArea = false`; Android already pads for the IME), and `src/shell/keyboard.ts` sets `data-keyboard` (the tab bar hides) when a text field has focus and the window is 120px+ shorter.
  - **Navigation:** React Router's view transitions for every navigation, `data-nav` push/pop/none from the paths (deeper in the same place, back up, anything else); mobile.css slides like a navigation stack, mirrored in RTL, a fade with Reduce Motion, nothing on iOS 17 (no view transitions). The swipe back on iOS is a JS edge swipe that goes up one level, not WebKit's back-forward gesture, which would also swipe back across tabs and sign-in screens. The items page's own phone slide is off when the app animates.
  - **Sheets:** `Dialog` and `Menu` are bottom sheets under 720px (web too); the menu renders into `<body>` there because the item toolbar's `backdrop-filter` would contain a fixed sheet, and its scrim swallows the tap.
  - **Native touches** as plugin commands from the web view: `haptic` on every toast (`onToast` in `packages/ui`: success, error, or a light tap), `set_appearance` (iOS `overrideUserInterfaceStyle`, so `system` hands back to the phone; Android bar icons and background), `share_file` (exports: the app swaps the web vault's `lib/download.ts` for one that opens the share sheet; the file goes to the app's temp folder or cache, never the App Group, and is deleted when the sheet closes). Plaintext JSON/CSV exports pass through that temp file, as the user asked for them.
  - **Testing:** Vitest for the shell (navigation, keyboard, appearance, haptics, downloads, the hover step, the bridge), a `Menu` test in the web vault, a toast-listener test in `packages/ui`, `ShellTest.kt` for the haptics and theme mapping, and the phone check (`pnpm --filter @octapass/mobile e2e`): the app's screens and shell on the mock vault in Chrome as a 390 × 844 touch phone, English and Arabic, asserting fields ≥ 16px on sign-in (with the Secret Key), sign-up, lock, search, editor, Settings and the export dialog, a non-zoomable viewport, no horizontal overflow, no hover rule without a pointer, bottom sheets, and the tab bar hiding for the keyboard.
