# 15 — Milestone 5: sharing backend (build contract)

The core and server side of plan 06: shared vaults, families, one-time share links and emergency access. The UI for these comes later, on top of this. Same rules as plans 11–14.

## Workstream N — branch `m5-sharing-backend`

**Owns:** `crates/octapass-core/src/sharing/**` (new), additive exports in `crates/octapass-wasm`, `apps/server/**`, `crates/octapass-api/**`, `docs/developers/sync-api.md`, `docs/features/{sharing,emergency-access}.md`. Additive changes only to existing core session code.

### Core (`sharing/`)
- **Sealed box:** seal a 32-byte key to an X25519 public key (ephemeral X25519 + HKDF-SHA256 `info = "openpass/v1/seal"` + XChaCha20-Poly1305, AAD binding `vaultkey:<vaultId>:<recipientAccountId>`), and open it with the account's private key.
- **Signed grants:** `grant = { vaultId, recipientAccountId, role, wrappedVaultKey, grantedBy, grantedAt }` signed with the granter's Ed25519 key. Recipients verify the signature against the granter's public key before using a vault key.
- **Key fingerprints:** a short, human-comparable fingerprint of an account's public keys (e.g. 6 groups of 4 digits, plus an emoji form) for out-of-band verification.
- **Member removal:** a new vault key, every item key re-wrapped under it (item bodies untouched), and new grants for the remaining members.
- **Share links:** encrypt an item snapshot with a random 32-byte key, giving `{ ciphertext }` for the server and a link fragment `#<key>` that never reaches the server. Optional access passphrase (Argon2id) mixed into the key.
- **Emergency access:** seal the ASK (or a chosen vault key) to the contact's public key, plus helpers for the release flow.
- Tests and test vectors for every construction.

### Server
- `POST /v1/vaults` (create a shared vault with the owner's grant), `GET /v1/vaults/{id}/members`, `POST /v1/vaults/{id}/members` (invite an existing account by email → grant; unknown emails get the same response with no grant, so no enumeration), `DELETE /v1/vaults/{id}/members/{accountId}`, `POST /v1/vaults/{id}/rotate` (new grants + re-wrapped item keys in one transaction), `GET /v1/accounts/lookup?email=` (public keys + fingerprint, rate-limited, only for signed-in users).
- Roles enforced on every write: `read` can't write, `write` can't manage members, `owner`/`manage` can.
- Families: `POST /v1/families`, invites, a shared Family vault, up to 6 members (configurable), leaving and removing members.
- Share links: `POST /v1/share-links { ciphertext, expiresAt, maxViews, passphraseRequired }` → `{ id }`, `GET /v1/share-links/{id}` counts a view and deletes the link at the limit or expiry (no account needed; strict rate limits), `DELETE` by the creator.
- Emergency access: `POST /v1/emergency-contacts` (sealed key + wait days 1–30), contact `request`, grantor `deny`/`approve`, automatic release after the waiting period, notifications by email (logged in dev mode), everything visible in the grantor's security log.
- Sync includes the vaults a member can access, with their grants. The WebSocket notifies all members of vault changes and membership changes.
- Account deletion: removes the account's grants, family membership, share links and emergency-access records (both directions), and deletes shared vaults it solely owns (already specified in plan 11).
- Integration tests for every endpoint, role checks, enumeration resistance, rotation, share-link view limits and expiry, the emergency-access timeline (use an injectable clock), and deletion cleanup.

## History
- 2026-10-24: created (overnight build plan).
- 2026-10-24: workstream N built (core `sharing/`, WASM exports, server, docs). Decisions and deviations:
  - **Sealed box** is `0x01 ‖ ephemeral public ‖ nonce ‖ ciphertext ‖ tag` (105 bytes); the version byte leaves room for hybrid ML-KEM. Its associated data uses the envelope convention, `"openpass/v1|" + context`, with contexts `vaultkey:<vaultId>:<recipientAccountId>`, `emergency:<grantor>:<contact>:ask` and `emergency:<grantor>:<contact>:vault:<vaultId>`.
  - **Grants** are signed over a length-prefixed encoding of every field (`openpass/v1/grant`, see the core README); `grantedAt` is Unix ms. The server checks shape and who may grant what, not the signature; clients verify before using a key. The granter's signing key is stored with each grant so it stays verifiable.
  - **Roles**: `owner` sits above `manage` (only owners grant or remove owners; the last owner can't leave). `VaultRole` gained `manage` and `VaultType` gained `family`. `VaultRecord` gained `keyId` and `grant`.
  - **Rotation** is its own call after `DELETE …/members/{id}`. It must name the synced revision (`409 vault-changed` otherwise) and cover exactly the members and items. Added: the server stores each shared vault's key id and refuses item keys wrapped under another key (`409 vault-key-changed`), so a member on the old key can't write items others can't open.
  - **Enumeration**: `POST …/members` and family invites answer `202` whatever the email. `GET /v1/accounts/lookup` has to return real keys (a key can't be sealed without them), so it answers `404` for unknown emails; it and invites share one per-account budget (20, then one per 30 s). Emergency contacts are named by account id from lookup.
  - **Families**: one per account; invites carry a `write` grant for the Family vault; `OCTAPASS_FAMILY_MAX_MEMBERS` (default 6, 2–100) counts members plus pending invites. Opt-in organiser recovery (plan 06) isn't in this milestone. `docs/self-hosting/configuration.md` (not this workstream's) should list the new variable.
  - **Share links**: ids are 16 random bytes; ciphertext up to 600 KiB; 100 open links per account; views limited to 10, then one per 6 s, per IP.
  - **Emergency access**: `view` works end to end (release endpoint + read-only sync of the grantor's vaults in scope); `takeover` is stored, but resetting the master password is left for the apps. Deny also takes back a released key. Notifications are email only (push comes with the push relay). Release happens in maintenance and lazily on every read, on an injectable clock (`AppState.clock`).
  - **Security log**: new `audit_events` table and `GET /v1/security-log`, with the emergency-access events for now, kept a year.
  - **Account deletion**: grants the deleted account gave members of surviving vaults keep its random id and public signing key (they're part of the signed message); everything else goes.
  - Clients still to follow: `packages/vault-client` types need `manage`, `family`, `keyId`, `grant` and the `membership-changed` message.
- 2026-10-24: workstream O (web vault round 2, branch `m5-web-sharing`) built the sharing UI and live sync on top of this. Decisions and deviations:
  - **Service shape**: the new calls live on a `SharingService` (`packages/vault-client` `types.ts`) reached through an optional `VaultService.sharing`, implemented by both the remote and the mock service. Optional because `apps/desktop`'s `TauriVaultService` implements `VaultService` too: the web UI hides sharing where it's missing. `VaultRole` gained `manage`, the new `VaultType` has `family`, `Vault` gained `untrusted`, `VaultMember` gained `accountId`, `fingerprint`, `verified`, `isYou` and `addedAt` (all additive). New error codes: `accountNotFound`, `notAllowed`, `alreadyExists`, `familyFull`, `quotaExceeded`, `untrustedVault`, `wrongPassphrase`, `invalidShareLink`.
  - **Vault names**: the server has no vault metadata, so a shared vault's name is an encrypted record inside the vault with overview type `vaultInfo` (title = the name, details `{ schemaVersion: 1 }`). The core keeps unknown item types (`ItemType::Other`), so it round-trips through key rotation like any item. Clients must hide `vaultInfo` records from item lists; the newest live one wins. Family vaults default to "Family". Other clients (extension, mobile) should adopt this convention.
  - **Grant checks**: a shared or family vault's key is used only after `openSharedVault` verifies its grant (rebuilt from the `VaultRecord` and this account's id). A grant that fails is marked `untrusted`: the vault stays listed with a warning, its items are dropped and writes refuse with `untrustedVault`.
  - **Fingerprints**: computed on the device with `keyFingerprint`, never taken from the server's `fingerprint` field. "Verified" is a per-account record on the device (account id → digits), so it lapses if the keys change. Adding someone shows their fingerprint and an optional "It matches" tick; it doesn't block, to keep sharing usable without a call.
  - **Rotation**: removing a member (vault or family) calls `rotate` right after the `DELETE`: sync, list members, `rotateVaultKey` over every record of the vault (hidden and undecryptable ones included), `POST …/rotate` with the synced revision, retrying `vault-changed` up to 3 times. After a family rotation, pending invites (which carry the old key) are cancelled and re-sent with a grant of the new key. Item writes that get `409 vault-key-changed` sync and try once more.
  - **Live sync**: the engine (worker) holds the `/v1/ws` connection while unlocked, re-authenticates a minute before the access token expires, reconnects with exponential backoff and jitter (1 s to 60 s) and with a fresh token after `4401`. `vault-changed` syncs when the revision is newer, `membership-changed` syncs and refreshes sharing screens, `session-revoked` signs out keeping only the Secret Key (as an expired session does), `account-deleted` wipes everything. The 30 s poll stays, but is skipped while notifications are arriving.
  - **Batch imports**: one `POST /v1/batch` per 1,000 items (or ~12 MiB). Writes aborted with `424` are sent again without the failing one, which becomes an import warning.
  - **Share links**: the snapshot leaves out `passwordHistory` and `favorite`. Links are `https://<web vault>/s/<id>#<key>`, plus `?server=<origin>` when the account isn't on the default server. The viewer fetches only when the visitor asks (each fetch counts a view, and chat apps preview links) and removes the key from the address bar once used. The device remembers which item each link came from (ids only) to list links by item title.
  - **Moving items** is copy-then-trash (the original stays in the Trash for 30 days), because the API has no cross-vault move. The editor's vault picker now applies to new items only; existing items move through Move to….
  - **Server bug found** (for workstream N): `POST /v1/vaults` and `POST /v1/families` read before they write inside a deferred SQLite transaction (`insert_vault` checks `vault_exists` first), so a concurrent write elsewhere (a WebSocket sign-in updating `last_seen`, another account's write) makes them fail with `500` from `SQLITE_BUSY_SNAPSHOT` (code 517). Fix there with `BEGIN IMMEDIATE` for SQLite writes, or by writing first. The client retries these two creates once, which is safe because the id is the client's and the failed attempt rolled back.
  - **Not done**: the emergency-access release can't be fast-forwarded in client tests (no dev clock hook), so server-backed tests release with `approve`; takeover is stored but acts like view.
- 2026-10-24: follow-ups from the second security review (branch `m6-server-followups`):
  - **Emergency contacts are rate limited.** Each new contact emails the contact, so adding (and removing and adding again, the only way to re-send) has two token buckets: 10 per account, then one every 15 minutes, and 5 per contact address from any account, then one per hour. Charged after validation, so malformed requests cost nothing; answered `429 rate-limited` with `Retry-After`; off with `OCTAPASS_RATE_LIMITS=off` like the others.
  - **A vault-scoped release no longer includes the grantor's account bundle.** The grantor's client already sealed only that vault's key for a vault scope (context `emergency:<grantor>:<contact>:vault:<vaultId>`), and `…/sync` already returned only that vault; but `…/release` also returned the grantor's bundle, whose `wrappedPrivateKeys` open every vault shared with the grantor and whose wrapped ASKs open everything. `EmergencyReleaseResponse.grantor` is now optional and sent for an account scope only. No client upload change was needed.
  - **Rotation re-seals pending family invites, or cancels them.** Chosen over cancel-only because it's atomic and the invitee notices nothing, while being as safe: `RotateVaultRequest` gained `invites`, a grant of the new key for each pending invite to keep (same role, one each, `400` otherwise), and any pending invite left out is cancelled in the same transaction, so no invite ever keeps the old key. The client seals to each invitee from a fresh lookup, and leaves out (so cancels) an invitee whose account is gone or whose keys don't match a fingerprint this device verified. This replaces the client's cancel-and-re-send after rotating.
  - **Invites can name their key.** `InviteRequest` gained an optional `keyId`; checked under the vault lock, a key rotated since answers `409 vault-key-changed`, so an invite racing a rotation is either stored first and then re-sealed or cancelled, or refused. `vault-key-changed` now carries a detail per case. The client sends it and seals once more on that answer.
