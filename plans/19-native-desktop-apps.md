# 19 — Native desktop apps

**Decision (maintainer, 2026-11-06):** the desktop apps move from Tauri (the web vault's screens in a web view) to native apps on the same Rust core. **SwiftUI on macOS first**, then WinUI 3 on Windows and GTK4 with libadwaita on Linux. The Tauri desktop app was to stay on each platform until that platform's native app has every feature (phase 4), the way plan 17 replaced the Tauri phone app. **On macOS it was dropped early** (maintainer, 2026-11-06: "We don't need the Tauri macOS app anymore, you can delete it, use the native from now."): the native app is Octa Pass on a Mac from now on, and the Tauri app is for Windows and Linux only (History, 2026-11-06). **It stays for Windows and Linux** until their native apps replace it (maintainer, 2026-11-07, asked whether to remove it all now: "keep it"), so its shared crates stay under `apps/desktop/crates`.

**Not changing:** the Rust core, the crypto, the server, the web vault, the browser extension and the CLI. The security model in plan 03 is unchanged; this removes a web view from the process that holds the open vault and adds nothing that weakens it.

## Why

- **Less attack surface.** The Tauri app renders decrypted items in a web view with an npm dependency tree. A rendering bug or a compromised package would run next to the open vault. A native app has neither.
- **Native feel.** Menus, keyboard shortcuts, the toolbar, Settings (Cmd+,), text selection, drag and drop, VoiceOver and full keyboard access, right-to-left Arabic: first-class only in native UI. The same reason as plan 17.
- **One Swift codebase on Apple platforms.** The iPhone and iPad app already runs on `OctaPassVault` with a split view for iPad. The Mac app compiles the same screens, so a fix or a feature reaches iPhone, iPad and Mac together.
- **The Mac extensions fit.** The AutoFill extension, Credential Exchange and the Safes File Provider are already Swift. With the app and extensions sharing an App Group store, as on iOS, AutoFill works without the app running.

**Considered and rejected:** rewriting the core in another language (Kotlin Multiplatform, C#/.NET, Go, Swift). Each would mean a second audited crypto implementation, a byte-for-byte compatibility risk for existing vaults, and a weaker WebAssembly story for the web vault and extension, for no gain: native UIs don't need it.

## Architecture

**One vault API for every native app.** The Mac app uses `OctaPassVault` (`crates/octapass-mobile` over `crates/octapass-mobile-vault`), the API the phone apps already use. It does not get a second UniFFI API over the Tauri app's `octapass-desktop-vault`.

```text
iPhone / iPad (SwiftUI) ─┐
Mac (SwiftUI) ───────────┼─ OctaPassVault (UniFFI) ─ crates/octapass-mobile-vault ─ octapass-ffi ─ octapass-core
Android (Compose) ───────┘          │
                                    └─ desktop services in Rust (phase 3): browser bridge, CLI session, SSH agent, auto-type
```

- **Why not the desktop vault:** the iPhone screens are written against `OctaPassVault`'s types. A second API would mean writing the Mac screens from scratch and keeping two vault crates forever. Desktop-only features move onto the shared vault instead, in Rust, with their tests (table below).
- **The crate keeps its name** (`octapass-mobile`) for now. Rename it to `octapass-native` when the Windows app starts, in one change, rather than now.
- **`DevicePlatform.macos`**: the Mac reports `macos`, as the Tauri app does.
- **No business logic in Swift**, as in plan 17: Swift draws screens and uses the Mac's services (Keychain, Touch ID, pickers, Quick Look, the pasteboard, menus).

### The Mac app

- **Where:** `apps/macos`, an XcodeGen project (`project.yml`, the `.xcodeproj` committed as on iOS), macOS 14+.
- **Shared screens:** the Mac target compiles `apps/ios/OctaPass/` directly. Differences are `#if os(macOS)` / `#if os(iOS)` in those files; Mac-only code lives in `apps/macos/OctaPassMac/`. No copies of iPhone files.
- **Shared packages:** `OctaPassVault` (its XCFramework gains macOS slices: arm64 and x86_64), `OctaPassResources` (strings and tokens), `OctaPassKeychain`, `OctaPassAutoFillKit` (with `OctaPassCore`, whose XCFramework has macOS slices too).
- **Shell:** the iPad's three-column `NavigationSplitView` (sidebar, list, item), a `Settings` scene, menu commands (New item, Lock, Find, copy password/username/code), a `MenuBarExtra` for quick access (phase 2).
- **Editing in the window:** a sheet on the Mac is a window of its own, so the item editor opens in the detail column, as in the web vault: a page on that column's stack (`DetailEditor`, `Route.editor`), on top of the item for Edit, in place of what was showing for a new item. Leaving it with unsaved changes (another item, another list) asks first. The list's rows open items on that stack themselves on the Mac, since a link from the content column doesn't reach it. The iPhone and iPad keep their sheets.
- **Activity and locking:** keyboard and mouse events count as activity (an `NSEvent` monitor instead of the iPhone's touch recogniser). Screen lock and sleep follow plan 18.
- **Identifiers:** the Mac app and its extensions use the iPhone app's App IDs (`app.octap.ios`, `app.octap.ios.autofill`, `app.octap.ios.safes`) and Keychain group (`<team>.app.octap.shared`): one universal purchase, so the App IDs' capabilities (AutoFill) serve both. Decided by the maintainer, 2026-11-06. The App Group is the Mac's own, team-prefixed (`<team>.app.octap`): with `group.app.octap` Finder's Safes failed with "Operation not permitted", because macOS opens a `group.` container only to a target whose own profile lists it, and Xcode signs the Safes extension (no capability that needs its own App ID) with the team's wildcard profile even with App Groups ticked. A team-prefixed group needs no profile, and an App Group never leaves the device, so it needn't match the iPhone's. They're apart from the Tauri app's `app.octap.desktop`, with their own store; since the Tauri Mac app was dropped without a migration (phase 4), nothing reads that store.
- **Signing:** development builds are signed with the team's Apple Development certificate (`apps/ios/Signing.local.xcconfig`). The data-protection Keychain and the App Group need it. There is no unsigned fallback that stores secrets somewhere weaker.
- **Desktop services and the sandbox** (decided by the maintainer, 2026-11-06): the app stays sandboxed. The browser bridge, the CLI session and the SSH agent listen in its App Group container, `~/Library/Group Containers/<team>.app.octap/` (`native-host.sock`, `cli.sock`, `agent.sock`), the one folder the app and the programs that connect can both reach. `octapass-native-host` finds it by its own signing team (it's signed with the app's, and is in the App Group), the CLI by the container that has `cli.sock`; `OCTAPASS_DESKTOP_DATA_DIR` still overrides both. There's no short fallback path on macOS (the sandboxed app's temporary folder is its own), so a user name long enough to push a socket path past 104 bytes makes that service fail to start, with the error in Settings. SSH clients are pointed at the agent by hand (`IdentityAgent` in `~/.ssh/config`, shown in Settings): the sandbox can't edit `~/.ssh`. The browsers' native messaging manifests are the one thing written outside the sandbox, with `com.apple.security.temporary-exception.files.home-relative-path.read-write` for the four Chromium browsers' `NativeMessagingHosts` folders (Chrome, Chromium, Edge, Brave) and Firefox's `Mozilla` folder (its shared folder, not its profiles, which are in `Firefox`): Firefox on a Mac may not have made `Mozilla` yet, and the sandbox couldn't make it with only `Mozilla/NativeMessagingHosts` allowed, so Connect left Firefox out (maintainer, 2026-11-07: widen it to `Mozilla/`). Firefox counts as installed when `Mozilla` is there or its app is in `/Applications`; acceptable because the app isn't on the Mac App Store. Auto-type stays out: a sandboxed app can't post keyboard events to other apps, so it needs a helper (later).

### Desktop features: where each goes

| Feature | Tauri app (its Mac code removed 2026-11-06) | Native Mac app |
|---|---|---|
| AutoFill (passwords, passkeys, codes) | Extension asks the running app over a socket | Extension reads the shared store through `octapass-ffi`, as on iOS; works with the app closed |
| Safes in Finder | `src-tauri/src/file_provider.rs` | File Provider extension, as `apps/ios/SafeProvider` |
| Credential Exchange | Swift shim linked with swift-rs | `onContinueUserActivity`, as on iOS |
| `otpauth://` links | `links.rs` | `onOpenURL`, as on iOS |
| Device unlock, stay unlocked | `device-unlock` crate | `OctaPassKeychain` and LocalAuthentication, as on iOS |
| Quick access, tray | Second web view, `tray.rs` | `MenuBarExtra` / panel in SwiftUI |
| Open at login | `login-item` crate | `SMAppService` |
| Browser extension (native messaging) | `bridge.rs` over the desktop vault | Ported to Rust on `OctaPassVault`; `octapass-native-host` and the protocol unchanged |
| CLI session | `cli_session.rs` | Ported the same way |
| SSH agent | `ssh.rs`, `ssh-agent` crate | Ported; the crate stays |
| Auto-type | `autotype.rs`, `autotype` crate | `OctaPassVault` call into the crate; values never reach Swift |
| Wi-Fi | `wifi` crate | CoreWLAN from Swift, or the crate; decided in phase 2 |
| SSO sign-in, service accounts | Desktop vault | Added to `OctaPassVault` (the phones lack SSO too, plan 17 History) |

## Phases

1. **Foundation.** macOS slices of the vault library; `DevicePlatform.macos`; `apps/macos` compiling the shared screens; the Mac shell (window, split view, Settings scene, menu commands, activity); sign up, sign in with two-step, unlock with the master password or Touch ID, browse, view and edit items. Runs next to the Tauri app.
2. **Mac platform parity.** AutoFill extension on the shared store, Safes File Provider, Credential Exchange, `otpauth://` links, quick access in the menu bar, open at login, plan 18's screen-lock rules, Wi-Fi.
3. **Desktop services on `OctaPassVault`.** Browser bridge, CLI session, SSH agent, auto-type, SSO, service accounts: each ported in Rust with its tests, the wire protocols unchanged.
4. **Parity and switch.** On macOS the switch came first: the Tauri app's Mac support was removed on 2026-11-06, before parity, and the docs say the Mac app is the native one. What's left on the Mac: a checklist against what the Tauri app did there (like 17a), finishing phase 3 (auto-type, and trying the services with a real browser, terminal and SSH server) and phase 2's untried pieces, and **Developer ID signing and notarization**, which aren't set up: the release workflow has no Mac job now, and `pnpm build:macos` makes a development-signed build only. **Migration of existing Tauri Mac installs is dropped** by the same decision unless the maintainer says otherwise: nothing reads the Tauri store (`~/Library/Application Support/app.octap.desktop`). People sign in again and their account vaults sync; a local vault has to be exported from the old app and imported. For Windows and Linux, phase 4 stays as planned: a parity checklist, migration of installs, signing, then the switch.
5. **Windows and Linux.** WinUI 3 (C#, `uniffi-bindgen-cs`) and GTK4 with libadwaita (Rust, calling the vault directly). Each gets its own section here when it starts.

## Testing

Rust logic stays covered by the vault crates' tests. The Mac app gets XCUITest UI tests against the development server, as `apps/ios/scripts/ui-tests.sh` does, plus the Swift packages' own tests on macOS.
