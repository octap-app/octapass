# 16 — Developer toolkit, integrations and the file safe

Octa Pass becomes more than a password manager: a secure **developer toolkit** (generate, inspect and use keys, certificates, tokens and hashes), **integrations** that hand secrets to the tools developers already use without copy-paste, and a **file safe** for encrypting files and folders on every system. Everything follows plan 03: keys are generated and kept on the device, encrypted in the vault, never sent to us.

Every tool exists in three places: the **CLI** (`octapass <tool> …`, scriptable, JSON output), the **apps** (a "Tools" section in the desktop app, web vault, mobile and the extension's app tab), and the **Rust core** (one implementation, tested once). Results can be **saved to the vault** as items with one click.

## 1. Generators

| Tool | What it makes | Saved as | Priority |
|---|---|---|---|
| **TLS/SSL certificates** | Self-signed certs; a private **local CA** (like mkcert: trust it once on this machine, issue certs for `localhost`, `*.test`, LAN IPs); CSRs with SANs; key types RSA 2048/3072/4096, ECDSA P-256/P-384, Ed25519; PEM, DER and PKCS#12 (`.p12/.pfx`) with a password | Certificate item (cert, key, chain, expiry) | P1 |
| **Certificate requests to real CAs** | ACME (Let's Encrypt, ZeroSSL): HTTP-01 and DNS-01 with common DNS providers; renewal reminders before expiry | Certificate item | P2 |
| **SSH keys** | Ed25519 / ECDSA / RSA, OpenSSH format, optional passphrase, `authorized_keys` line, fingerprint; served by the SSH agent (plan 05) | SSH key item | P1 |
| **GPG / age keys** | OpenPGP keys for signing commits and email; age keys for file encryption | Key item | P2 |
| **API keys and secrets** | Random tokens in common shapes: hex, base64url, base62, prefixed (`sk_live_…`), UUID v4/v7, ULID, NanoID; length and alphabet options | API credential item | P1 |
| **JWT signing keys** | HMAC secrets (HS256/384/512), RSA (RS/PS), EC (ES256/384), Ed25519 (EdDSA); exported as PEM and **JWK / JWKS** | Key item | P1 |
| **Password hashes for apps** | Argon2id, bcrypt, scrypt, PBKDF2 hashes in standard PHC/modular format, with tunable cost and a "verify" mode | Not saved by default (they aren't secrets) | P1 |
| **TOTP secrets** | New 2FA seeds plus their QR code, for developers adding 2FA to their own apps | One-time code item | P1 |
| **Passwords and passphrases** | (exists) | Login / Password | — |

## 2. Inspectors and converters (offline, nothing leaves the device)

| Tool | Does | Priority |
|---|---|---|
| **JWT / JWS / JWE reader** | Decode header and payload, show claims in plain language (expires in 12 min, issued by, audience), **verify the signature** against a secret, PEM or a JWKS URL, flag `alg: none` and expired or not-yet-valid tokens; create and sign JWTs from claims; decrypt JWE with a key you hold | P1 |
| **Certificate reader** | Paste PEM / load a file / point at `host:443`: subject, SANs, issuer chain, expiry, key type, fingerprints, problems (expired, weak key, SAN mismatch) | P1 |
| **Hashing** | SHA-1/224/256/384/512, SHA-3, BLAKE2/BLAKE3, MD5 (legacy checks only, labelled as such), CRC32; text or files; HMAC with a key; compare a file against a published checksum | P1 |
| **Encoding** | Base64, base64url, base32, hex, URL encoding, HTML entities, Unicode escapes; auto-detect the format of a pasted string | P1 |
| **Key converters** | PEM ↔ DER ↔ JWK ↔ OpenSSH ↔ PKCS#8/#1; public key from private key; fingerprints | P1 |
| **Random data and UUIDs** | Cryptographic random bytes in any encoding, UUID v4/v7, ULID | P1 |
| **QR codes** | (plan 01) | — |

## 3. Integrations: use secrets without copy-paste

| Integration | How | Priority |
|---|---|---|
| **CLI secret references** | `octapass://Vault/Item/field` in `.env` files and config; `octapass run -- npm start` injects them as environment variables; `octapass read`, `octapass inject -i tpl -o out` (plan 05) | P0 (CLI) |
| **Any developer tool (API clients, scripts, IDEs)** | **"Octa Pass Connect"**: one generic, local, authenticated helper (CLI or desktop app) that any tool can ask for a secret by reference, approved per app on first use, plus `octapass run` / `octapass read` for anything that reads environment variables or files. No integration is built for one specific product. API clients such as Postman, Insomnia or Bruno use it through their existing environment-variable or script features. | P1 |
| **API credentials with live tokens** | An API credential item can hold an OAuth2 client (client-credentials or refresh-token flow): Octa Pass fetches and refreshes the bearer token, shows its JWT claims and expiry, and hands the current token to any tool through Connect or the CLI | P2 |
| **Git** | Credential helper (`git-credential-octapass`); commit signing with SSH or GPG keys from the vault | P1 |
| **SSH agent** | (plan 05) Keys from the vault, approval per use, works with `ssh`, Git and IDEs | P1 |
| **Cloud and DevOps** | AWS `credential_process`, `kubectl` exec credential plugin, Docker credential helper, Terraform/Pulumi via `octapass run`, GitHub Actions / GitLab CI with service-account tokens (read-only scoped access to one vault) | P2 |
| **IDEs** | VS Code / JetBrains extension: browse references, insert `octapass://` links, run with secrets injected | P2 |
| **Browser extension** | Detect API keys pasted into forms and offer to save them; fill bearer tokens into developer portals | P2 |

**Service accounts** (P2): non-human access for CI and servers. A token bound to one vault, read-only by default, revocable, every use in the security log.

## 4. The file safe

There's no secure way to "lock" a normal folder with permissions: an administrator, another OS or a disk tool can still read it. Real protection means **encrypting** the contents. Octa Pass offers three levels:

| Feature | What it is | Priority |
|---|---|---|
| **Encrypt / decrypt files** | Right-click a file or folder → "Encrypt with Octa Pass" (Finder Quick Action, Explorer context menu, Nautilus/Dolphin actions, and `octapass encrypt`/`decrypt`). Uses the **age** format, so files stay openable even without Octa Pass. Encrypt for yourself, for other Octa Pass users (their public keys) or with a passphrase. | P1 |
| **Documents in the vault** | Files as encrypted vault items (attachments, plan 01): synced, shareable, part of the 1 GB quota | P1 |
| **Octa Pass Safe** (an encrypted drive) | A folder that **appears as a normal drive or folder** while unlocked and is encrypted when locked, on macOS (File Provider extension), Windows (Cloud Files API / WinFsp), Linux (FUSE) and in the mobile apps' Files integration. File contents and names are encrypted per file, so it syncs efficiently. It locks with the vault and opens with device unlock. Optional sync across devices through the server. | P2 |
| **Secure delete** | Overwrite-and-delete the plaintext original after encrypting, where the file system allows it (honest about SSDs and copy-on-write file systems) | P1 |

## 5. Where it appears in the apps

- **Desktop app:** a "Tools" section in the sidebar (generators, inspectors, file encryption), drag and drop of files and certificates, the quick-access window (`Cmd+Shift+Space`) with tool commands such as "decode jwt" and "uuid", and Octa Pass Connect running in the background.
- **Web vault:** the same Tools section, everything computed in the browser by the WASM core. No file drive.
- **Extension:** the web vault's Tools section, in the app tab (since 2026-11-07; before that the popup had a quick JWT decode, hash, encode and random secret).
- **Mobile:** generators, inspectors, the QR scanner, and Files integration for the safe.
- **CLI:** every tool, script-friendly, with JSON output and stdin/stdout piping.

## 6. Security rules

- Private keys are generated on the device by the core, stored only encrypted in the vault, and shown or exported only after re-confirming (master password or device unlock).
- Inspectors work offline. Fetching a JWKS URL or `host:443` is the only network use, and it's shown to the user.
- Octa Pass Connect listens only on a local socket or loopback port with per-client approval and a session token. Every secret it hands out is recorded in the security log.
- "Lock a folder" is always backed by encryption, never by permissions alone.

## Roadmap

**Inside 1.0** (maintainer decision, 2026-11-02). This supersedes the earlier decision of 2026-10-23 that the toolkit would start after 1.0. Every row in this plan, P1 and P2, is required for 1.0, and phases A to C are roadmap phase 8 in [plan 09](09-roadmap.md). Sections 1, 2 and 5 (the developer toolkit) are built; see History.

- **Phase A:** the core crypto toolbox (generators, inspectors, encodings, hashes, QR codes, converters), the CLI commands, a Tools section in desktop and web, file encrypt/decrypt (age) with context menus, and Octa Pass Connect.
- **Phase B:** SSH agent, git helpers, certificate reader for live hosts, local CA trust, service accounts, CI integrations.
- **Phase C:** Octa Pass Safe (encrypted drive) on the three desktop systems, then mobile; ACME certificates; OAuth live tokens; IDE extensions.

- 2026-11-02: the file safe, §4 (branch `m25-file-safe`; everything here is inside 1.0 by the maintainer's decision of that date). **File encryption:** `octapass encrypt`/`decrypt` on the `age` crate, with folders as tar inside age (`.tar.age`, so `age -d | tar x` works). Interop is checked both ways against the reference Go tool. **Secure delete:** one random pass, then rename and remove; `Guarantee::Overwritten` is claimed only for ext4/XFS on a rotational disk, and everything else, unknown storage and all of Windows included, is `BestEffort` with the reason shown before and after. **Right-click menus:** per-user files or `HKCU` keys that only start a program. The desktop app takes `--files <action> <paths>`: a second process leaves the request in a folder and the running app picks it up, because macOS can't pass arguments to a running app and Explorer starts one process per file. **Decisions:**
  - **"Yourself" is a derived file identity, others are account keys.** `HKDF(account X25519 private key, info "openpass/v1/age-identity")` gives one key on every device with nothing new stored or synced, and it can be exported for `age -d -i`, which is what "openable without Octa Pass" needs. The account key itself can't be exported, because it also opens shared vault grants. Other users are reached through their existing published X25519 key, so the server needed no change. **Consequence for key rotation:** rotating an account's X25519 pair would strand files encrypted to the old one and change the file identity; a rotation design must keep the old private keys for decryption. (Rotating the ASK or vault keys doesn't touch either.)
  - **The Safe format uses no deterministic encryption.** Filesystem encryption tools usually encrypt names deterministically (EME, AES-SIV) so that a path can be looked up on disk. A Safe instead keeps names only inside per-object records, sealed with the ordinary envelope, and reads every record when it opens. That's a new primitive avoided, and it also hides the tree's shape, at the cost of reading all records at open.
  - **A Safe's key is a `fileSafe` item in the personal vault**, hidden from item lists like `maskedEmailProvider`. So it locks, syncs, recovers and survives vault key rotation with no new key path. Personal vault only: a shared vault would give the key to members, and removing one couldn't rotate it without re-encrypting the Safe.
  - **Sync reuses attachments.** A synced Safe's blobs are attachments of its item, unlisted in its details. No server change, no migration, and quota, deletion and the per-file limit come with it. The limit means files above it (100 MiB by default) stay on the device, and sync says so. The Safe's own rule set handles conflicts: an edit beats a deletion, and two edits keep both as `(conflict <date>)` copies.
  - **Writes are staged, encrypted, and sealed on flush**, instead of per-block random nonces in place (gocryptfs, Cryptomator): whole-file STREAM keeps truncation and reordering detection, at the cost of rewriting a file on each flush.
  - **Windows is Cloud Files, not WinFsp:** no kernel driver to install. The price, shared with File Provider on macOS, is that the OS keeps hydrated plaintext on disk for opened files while unlocked. Both are removed on lock and at start-up; a crash leaves them until the next start. FUSE has no such copy.
  - **macOS keeps every key in the app.** The File Provider extension holds no key and no Safe code, and asks the running app over the audited App Group socket, as AutoFill does.

- 2026-11-02 (branch `m25-dev-toolkit`): sections 1, 2 and 5 built. One entry point: the core's `tools::toolkit::run(op, json) -> json` (`toolkit` feature), which the CLI, WASM (`toolRun`) and the native apps (`toolkit_run`) all call, so a new tool needs no new binding. **Decisions:**
  - **A separate WASM build.** The web vault's own build leaves the toolkit out; its worker loads `dist/tools` (toolkit + OpenPGP) when the Tools section is used, so signing in stays a small download. The extension and desktop already have what they need.
  - **`crates/octapass-net-tools`** holds the only network and OS access: `tls::probe` (handshake only, nothing sent), `fetch::jwks`, the ACME client, DNS-01 providers and the system trust store. The core stays free of I/O. The CLI and desktop share it.
  - **X.509 is assembled from `x509-cert` types, not its builder**, so every signature goes through `toolkit::keys` and works on WASM (the builder reads the system clock). PKCS#12 uses `pkcs12` 0.1's types and KDF rather than `p12-keystore`, which pulls a second RustCrypto generation. Files are PBES2 with AES-256-CBC and an HMAC-SHA-256 MAC, 600,000 rounds. Reading also takes legacy 3DES and RC2 files; nothing is written with them, so very old importers may refuse ours.
  - **Local CAs are name-constrained by default** (critical `nameConstraints`: `localhost`, `test`, `local`, `internal`, `home.arpa`, loopback, RFC 1918, link-local), `pathLen` 0. `--unconstrained` opts out and warns. Issuing checks the constraint too, so the error comes at issue time rather than in a browser.
  - **RSA private-key operations (RUSTSEC-2023-0071, Marvin):** re-checked as this plan's 2026-10-25 entry requires. `rsa` is still 0.9 with the advisory open. The toolkit signs (RS/PS, X.509) and decrypts (RSA-OAEP JWE) with RSA through the blinded operations, one at a time, at the user's request on their own device. Marvin needs an attacker timing many operations, and there is no oracle here, so this is accepted for the toolkit. It says nothing about the SSH agent, which answers remote requests.
  - **JOSE follows RFC 8725.** The header never chooses how a key is read; HS* takes only a secret or `oct` JWK; `none` never verifies; any `crit` header fails; RSA1_5 JWE is refused; PBES2 counts are capped at 1,000,000; a `zip` payload stops at 1 MiB; ECDH `epk` points are validated by parsing. Compact and flattened JSON serializations are read; general JSON isn't. X25519 ECDH JWE isn't built.
  - **Password hashes** enforce OWASP floors when hashing, and ceilings when verifying, because a pasted hash can ask for any cost. bcrypt refuses over 72 bytes instead of truncating.
  - **`certificate` and `key` item types** (additive, as `sshKey` was). CXF has no credential for them, so they export as custom fields with secret parts concealed. Certificates and keys are created from Tools, not the item editor, which edits only notes and custom fields. API keys save as `apiCredential` (from `m25-item-types`) and TOTP secrets as a login with `totp`.
  - **age keys** use `bech32` 0.9 and the core's X25519, the same `bech32` as `m25-file-safe`, so the toolkit needs no `age` crate.
  - **ACME:** `--agree-tos` is required, nothing is sent without it. Tokens are checked against the base64url alphabet before they name a file (no `../` from a hostile CA). Plain `http://` directories work only for loopback. No specific DNS host is privileged: the hook covers all of them; Cloudflare and DigitalOcean are built in because they need only a bearer token. Renewal reuses the account key kept in the item, and the reminder window is a third of the lifetime, at most 30 days.
  - **Section 6:** generators never print private keys on a terminal; the apps show them only through the identity gate; `cert export` and `key export` ask for the master password again.
- 2026-11-07: three Safe fixes in the native apps (maintainer's report). **A Safe kept on one device is listed only there:** its item syncs with the vault like every Safe's (the vault is where its key lives), so every device listed it and opening it made an empty Safe there. A device-only Safe made by the Mac, iPhone or Android app now names its device in the item (`device`: a random id per install, in the data folder's `device-id`, not a secret, only inside encrypted items), `list_safes` leaves out another device's, and `open_safe` refuses one that isn't listed, so no empty folder is made. One made before this has no `device` and lists where its folder is. The Windows and Linux app and the CLI never name a device and hide a named one. **Deleting a Safe another device deleted first:** the trash call sent this device's older revision, the server refused it, and nothing synced, so the Safe stayed. A refused trash or restore now syncs and succeeds when the item is already where it was going (or gone). **Synced Safes sync on their own on the Mac and iPhone,** as the Tauri app's did: a few seconds after a change in the app or in Files/Finder (the extension posts the `safes.changed` Darwin notification), after each vault sync, and every two minutes while unlocked. Android followed the same day: `SafeDrives.syncSoon` runs a few seconds after each change the documents provider makes (its one `notifyChildren` point), after each vault sync, and every two minutes while unlocked, one round at a time on the drives' own coroutine scope.
