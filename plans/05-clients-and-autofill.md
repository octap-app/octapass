## Server selection (hosted-first, self-host capable)

- Every app ships one binary that works with the **free Octa Pass service (default)** and with **self-hosted servers**.
- Sign-in screen: the server is "Octa Pass" by default. A "Server" option reveals **Self-hosted** with an HTTPS URL field. The server is stored per account. Multi-account switching is P1.
- The app checks `GET /v1/server-info` (version, features, push relay status) and shows a clear error for incompatible or non-HTTPS servers.
- **Push on mobile:** Apple and Google only accept pushes signed with our credentials, so self-hosted servers use the opt-in **push relay** (plan 04). Without it, mobile apps sync on open, in real time while open, and with OS background refresh.
- **F-Droid build (P2, required for 1.0):** no Firebase; background sync by polling.

## Local mode in the clients

- First-launch screen: **Create account** (default), **Sign in**, and **Use on this device only**.
- Local vaults use the same UI. Server-only features are shown disabled with a short "Needs sync" note and a **Turn on sync** button, never hidden in a way that confuses people.
- Backup reminders appear in the health dashboard ("Last backup 34 days ago").
- Browser extension: the vault is stored in the extension's IndexedDB, wrapped with the desktop app's chip-backed key over native messaging when the desktop app is installed. Otherwise it relies on a strong master password (plan 03).
- Order of delivery: extension (phase 2), desktop (phase 3), mobile (phase 4). The web vault never offers local mode (a website isn't a safe place for a server-less vault).

## Browser extension

**Structure**
- `background` service worker: holds the unlocked core (WASM) and sync. MV3 service workers are killed when idle, so ASK is kept in `chrome.storage.session` (memory-only, never written to disk) wrapped with a per-session key. Auto-lock follows the user's timer, except with **stay unlocked** on (plan 18, the default): then there is no timer and no lock on system lock, the vault stays in that memory until the browser closes, and with the desktop app staying unlocked the extension opens through it with no prompt (at browser start and on its lock screen).
- `content` script (isolated world): form detection, in-page UI.
- `page` script (MAIN world, minimal): intercepts `navigator.credentials.create/get` for passkeys and forwards requests to the content script.
- App page (`app.html`), opened in a browser tab by the toolbar button: the web vault's layout and screens, with "This site" first in the sidebar. No popup and no side panel (History 2026-11-07).
- Native messaging host (installed by the desktop app): biometric unlock and shared session with the desktop app.

**Form detection**
- Heuristics: `autocomplete` attributes first, then input types, names/ids/labels/placeholders in the 10 most common languages, and form structure (multi-step login, identifier-first).
- Field classifier scored with a small rule engine (no remote ML). Per-site overrides ship as a signed JSON ruleset, updated with the extension (no remote code).
- Shadow DOM and same-origin iframe support. Cross-origin iframes only with an explicit per-origin approval: the inline menu asks first, naming the frame's host and the top site as the browser reports them, and the answer is kept per (top site, frame origin). Frames from the same registrable domain need none. Built in M6 (plan 13's History).

**Filling rules** (security, see plan 03)
- Suggestions show only for logins saved for the page's own part of a site (History 2026-11-05). With the default match mode (`subdomains`), for a page on host H (a leading `www.` counts as the bare host on both sides), a login saved on host S is offered when S is H (listed first), when S is a domain above H on the same registrable domain (`example.com` or `b.example.com` for `a.b.example.com`, listed next, nearest first), or when S is below H (`login.example.com` on `example.com`, listed after those). A login on another part of the same domain (`shop.example.com` on `login.example.com`) isn't offered and is never filled automatically: it's one tap away under **Logins for other parts of example.com**, and filling one from there offers to add H to that login. Equivalent domains come after all of these. Registrable domains come from the PSL, so `alice.github.io` and `bob.github.io` stay apart. Per-URL modes still win: `baseDomain` (any host on the registrable domain, the old default), exact host, starts with, regex, never. Passkeys follow WebAuthn's rpId rules, not this.
- Fill needs a user gesture: clicking our inline icon/menu, the keyboard shortcut, or Fill in the app tab's "This site". The one exception is **fill on page load** in the browser extension (History 2026-11-06): off by default, one per-device switch ("Fill logins when a page opens"), never synced. With it on, a login form in the top frame of an `https://` page is filled as it shows, with no gesture, only when all of these hold: the vault is unlocked; filling wouldn't ask first (the "ask on every fill" gate is off or stay unlocked is on); the login is saved for the page's own host (match quality `exact`: not a domain above or below it, not equivalent domains, never another part of the site, never http); its account and password fields are empty, visible and uncovered; and it's the login last used there (usage stats), or the only one. A fill on load isn't counted as a use. Typing over a filled account clears it and its password; typing over the password clears only the password; a click still opens the full list. Same-origin frames, cross-origin frames, sign-up and change-password forms get nothing on load.
- The in-page menu is rendered in an extension-origin iframe or the top layer and protected against overlay/clickjacking tricks.

**Suggested strong passwords**
- Triggered on fields that look like *new* passwords: `autocomplete="new-password"`, a second "confirm password" field, or sign-up / change-password form heuristics.
- The inline menu shows **"Use suggested password"** with a preview (`Lantern-ruby-T7#qv-42` style). It's generated on the device with the user's default settings, adjusted to the site's rules when known (Apple's `password-rules` dataset, P1, or the field's `minlength`/`maxlength`/`pattern`).
- One tap fills the password and its confirm field, and **immediately saves a draft login** (URL + username if present + password). Then the user can't lose it if the sign-up succeeds but the save prompt is dismissed. The draft becomes a normal login after a successful submit, or stays as "Unconfirmed" for 7 days.
- Change-password forms: the old password is filled from the matching login, the new one suggested, and the old one moves to password history.
- Also offered: "Use a masked email" for the email field of sign-up forms (plan 06).
- **Android:** the Autofill Service returns a "Suggested password" dataset for new-password fields, and Credential Manager handles `createPassword`. **macOS/iOS:** offered where Apple lets third-party credential providers fill or save new passwords; otherwise from the app's quick generator (copy and auto-clear). **Desktop auto-type:** "Type new password" from the quick-access window.

**Save/update** detection on submit, `fetch`/XHR completion and SPA navigation. Prompts appear after a successful navigation when possible, so failed logins aren't saved.

**Saving while locked** (plan 03, *Saving while locked*; History 2026-11-05): saving never requires unlocking. While Octa Pass is locked nothing can be compared with the vault, so the prompt always says **Save** (with a line saying it's added at the next unlock), never Update, and never stays quiet because the login is already saved. Save seals the entry into the device's save inbox; the next unlock merges it: a new login (or address, card, API key) tagged **Unconfirmed** for review; a new password on the login with that site and username, the old one in its history and its review mark left as it was; exact duplicates dropped. The never-save list still applies. No inbox key yet (no unlock on this device since this shipped) or a full inbox (50): nothing is offered in the browser extension, and Android asks to unlock as before. Signed out: nothing to save to, as before. A suggested-password draft is saved at once only while unlocked; locked, the submit asks like any other save.

**Cards and identities:** detection of `cc-*`, `address-*`, `name`, `email`, `tel` autocomplete tokens and heuristics. CVV is filled only after re-authentication if the user enables "re-prompt". Submitted address and card forms get a save/update prompt like logins; the CVV is stored only if the user ticks it on that prompt (see History).

**The newer item types** (History 2026-11-08): bank accounts, databases, software licences, ID documents and crypto wallets fill like cards, only in fields the engine recognises as theirs and only after a pick; API credentials keep the login rules. A wallet fills an address, never its seed phrase or passphrase; a bank account never fills its PIN.

**The browser's own password manager:** the extension offers to turn it off ("Use Octa Pass instead of <browser>'s password manager") through `chrome.privacy.services`, behind the optional `privacy` permission (see History).

**Store distribution:** Chrome Web Store, Microsoft Edge Add-ons, Firefox Add-ons (AMO, with source upload for review), Opera add-ons. Reproducible build instructions in the docs.

## Passkeys

- **Browser:** the MAIN-world script wraps `navigator.credentials.create/get`. When the user picks Octa Pass, the core acts as the authenticator: it checks the `rpId` against the page origin, signs with the stored key, and returns a `PublicKeyCredential`-shaped response. "Use another device / platform authenticator" falls back to the browser's original implementation.
- **Apple:** `ASCredentialProviderViewController` with passkey support (`ASPasskeyCredentialRequest`); register identities with `ASCredentialIdentityStore` so passkeys and passwords show in the QuickType bar.
- **Android 14+:** `CredentialProviderService` for passkeys and passwords. Below 14, passwords use `AutofillService`.
- **Windows 11:** third-party passkey plugin provider API (`crates/windows-passkey`, History 2026-11-02). It needs the app's MSIX package; the NSIS install keeps using the browser extension.
- **Backup/sync:** passkeys are ordinary encrypted items, so they sync like everything else (BE/BS flags = true).
- **Import/export:** FIDO Credential Exchange Format (CXF), plus the Credential Exchange Protocol on Apple/Android when available.
- **Unlock with passkey (PRF):** an Octa Pass account passkey with the PRF extension can unwrap ASK, as an alternative to typing the master password on supported browsers (P1).
- **PRF on Octa Pass's own passkeys** (maintainer, 2026-11-07: "Add PRF support"): passkeys Octa Pass makes answer the WebAuthn PRF extension, so a site, or the extension's own Unlock with Touch ID, can keep its passkey in Octa Pass.
  - **Secret:** each new passkey gets a 32-byte random `prfSecret` in its record, inside the item's encrypted details like the private key. Passkeys made before it have none and answer without PRF.
  - **Output:** the standard one, `HMAC-SHA-256(prfSecret, SHA-256("WebAuthn PRF" ‖ 0x00 ‖ input))` for `first` and `second`. Octa Pass always verifies the user, so there's one secret (CTAP's `credRandomWithUV`). Creation reports `enabled: true` and gives `results` when `eval` was passed; an assertion uses `evalByCredential[credential id]`, else `eval`.
  - **Where:** the core, the phones' and Mac's `octapass-ffi` (`PasskeyCreationRequest.prf`, `PasskeyAssertionRequest.prf`, outputs on `PasskeyRegistration` and `PasskeyAssertion`), and the Apple AutoFill extensions on iOS 18 and macOS 15 (`extensionInput.prf` in, `extensionOutput` with `prf` out). The JSON forms parse `extensions.prf`, so Android's `requestJson` and the extension's own pages get it from the same code once they pass it.
  - **Apple's salts:** Apple's API hands the provider `saltInput1` and `saltInput2` without saying whether the system has hashed them. Octa Pass treats them as the page's raw input, as the core does everywhere, so the output matches the other Octa Pass platforms if that's right. Saving and unlocking on the same Mac or iPhone go through the same code either way. **To verify** with a page that prints the PRF result in Safari and in Chrome.
  - **The extension's own passkey:** the page asks for its extension ID (`oojck…`, 32 letters `a`–`p`) as its RP ID, but Chrome hands authenticators, the macOS provider among them, the extension's origin `chrome-extension://<id>` instead (Chromium's `MaybeGetRelyingPartyIdOverride`), and hashes that into the rpIdHash it checks. For platform requests (client data by hash, where the browser has already checked the origin) the core accepts both forms and keeps the RP ID exactly as given; the new login's address is `chrome-extension://<id>`. Accepting only the bare ID (2026-11-07) still refused Chrome's requests (maintainer, 2026-11-08). Every other non-domain RP ID is still refused, with "Octa Pass saves passkeys for websites only. Save this one in Passwords or on a security key."
  - **Security:** the PRF secret is a key like the passkey's private key, encrypted and synced the same way (plan 03). Keeping the extension's unlock passkey in Octa Pass isn't circular on a device whose AutoFill extension unlocks by itself (Touch ID or the master password), but it is on a device where it can't: then use Passwords or a security key. The extension's other unlock, through the Octa Pass app, needs no passkey.

## Desktop (Tauri 2)

- React UI from `packages/ui`. The Rust side links `octapass-core` directly; the frontend never sees keys, only decrypted fields it asks for.
- Global quick-access shortcut (search, copy, auto-type).
- **Running in the background:** closing the vault window hides it; the app keeps serving quick access, the browser bridge, the agents, the CLI and AutoFill. A tray icon (the menu bar on macOS) has Show, Quick access, Lock and Quit, and the app opens at login, hidden and locked. Both are on by default, per device, and can be turned off in Settings (see History, 2026-11-04). A force quit or a crash doesn't take the icon away: a watchdog starts the app again, hidden, until it's quit on purpose (History, 2026-11-09; the Mac app's is in plan 19).
- **Auto-type:** types username ⇥ password ↵ into the focused window, after checking the window title/app matches the item (Windows: SendInput; macOS: CGEvent + Accessibility permission; Linux X11: XTest; Wayland: `xdg-desktop-portal` RemoteDesktop where available, otherwise clipboard with auto-clear).
  - The sequence is per item (`details.autoType.sequence`): `{USERNAME}`, `{PASSWORD}`, `{TOTP}`, `{TAB}`, `{ENTER}`, `{DELAY n}` (ms, at most 10 000), other text literally, `{{}`/`{}}` for braces. Default `{USERNAME}{TAB}{PASSWORD}{ENTER}`; `password` items `{PASSWORD}{ENTER}`. Characters are Unicode key events (keysyms on Linux), so layouts and non-ASCII text don't matter.
  - Window match: the item's `details.autoType.windowTitles` (contains, or a `*`/`?` glob over the whole title or app name) always count. In a known browser only the page address counts, matched to the item's URLs like the extension does; page titles never count (a phishing page writes its own). The address is read only on macOS (Accessibility `AXURL` of the web area). In other apps the title or app name must contain the item title or its domain's name (≥ 3 characters).
  - Refused: Octa Pass's own windows, a locked screen, modifier keys still held, focus moving away during typing (checked before every key group).
  - Database items type too (History 2026-11-08): `{USERNAME}` and `{PASSWORD}` are the database's, with the default sequence, and their window must match by title like any other app's.
  - Triggers: Cmd/Ctrl+Enter in quick access types into the window quick access opened over; `Cmd/Ctrl+Shift+\` types the only login for the focused window, or opens quick access with the matches. Wayland can't see the focused window, so there only an explicit quick-access pick types.
- **macOS AutoFill provider:** a sandboxed Credential Provider extension (`app.octap.desktop.autofill`) in the app bundle. Unlike iOS it has no store of its own: it asks the running app over a Unix socket in the app group container (`<team>.app.octap.desktop`), and the app checks the peer's audit token (its own bundled extension, its own team's signature on release builds) before answering. Passkeys sign the system's client data hash (`ClientData::Hash`), as on iOS.
- Native messaging host for the browser extensions (biometric unlock, single unlock across apps).
- SSH agent: serves SSH keys, with an approval that lasts 15 minutes per unlock (plan 16 History, 2026-11-09).
- Updates: Tauri updater with signed manifests. Linux via repositories/Flatpak.
- Biometrics: Touch ID (LocalAuthentication + Keychain/Secure Enclave), Windows Hello (`UserConsentVerifier` + `KeyCredentialManager`).

## Mobile

- Main app UI: native SwiftUI and Jetpack Compose on the Rust core (plan 17). The earlier Tauri 2 app stays until the native apps reach parity.
- **Autofill extensions are native and small** (Swift/Kotlin + UniFFI core) because of memory limits (iOS credential extensions get ~120 MB). They share the encrypted store with the app through an App Group (iOS) or the app's private storage (Android, same process/user).
- Camera QR scanner for TOTP. Share sheet: "Save to Octa Pass".
- **Save without unlocking (Android):** Save on the system's "Save to Octa Pass?" sheet seals the login into the store's save inbox from the Autofill service itself and shows "Saved to Octa Pass" (plan 03, *Saving while locked*). The app's next unlock, or the next unlock in an autofill screen, whichever comes first, merges it. Only when the inbox can't take it (no unlock here has pinned its key yet, or it's full) does the unlocking Save screen open, as before. **iPhone:** iOS gives AutoFill extensions no save request, so there is no save flow to change.
- **Unlock in autofill extensions:** the iOS AutoFill extension and the Android Autofill/Credential provider unlock with the device's own lock: Face ID / fingerprint, or the device passcode / screen-lock PIN when biometrics aren't available, then the master password (same keys as the main app via the App Group / Keystore; see plan 03 *Device unlock rules*). The browser extension offers a device passkey (Touch ID, Windows Hello incl. its PIN, phone passcode), unlock through the desktop app, or the master password. On devices with no lock at all, the two device-auth gates (plan 03) follow Google Password Manager: opening an already-unlocked vault and filling don't prompt; after a restart or lock the master password opens it, and reveal/copy/export always ask for it.
- Screenshot protection on sensitive screens (Android `FLAG_SECURE`; iOS blur on app switcher).
- Watch apps (P2, required for 1.0): TOTP codes on Apple Watch / Wear OS.

## CLI

```
octapass login [--server URL]          octapass unlock
octapass list [--vault V] [--search Q] octapass get <item> [--field password]
octapass totp <item>                   octapass generate [--words 5 | --length 24]
octapass run --env-file .env.octapass -- npm start   # resolves octapass:// references
octapass import <format> <file>        octapass export --format cxf|json|csv [--encrypted]
```
Session keys live in the OS keyring, or in the desktop app over IPC when it's running.

## Autofill quality program

- `tools/autofill-corpus/`: saved, anonymised snapshots of the top 500 login, signup, card and address pages, plus synthetic edge cases (iframes, shadow DOM, multi-step, SPA).
- CI runs the extension against the corpus. Every regression in fill accuracy blocks the release.
- Users can report "autofill didn't work here" with an opt-in, content-free form-structure report (field types, no values).

- 2026-10-24: CLI built in `apps/cli` (crate `octapass-cli`, binary `octapass`, in the root Cargo workspace) with every command above except `export --format cxf` and `--encrypted`, plus `lock`, `logout`, `status` and `read`. Docs: `docs/platforms/cli.md`. Decisions and deviations:
  - **Reuses the desktop vault.** `octapass-desktop-vault` (sync client, encrypted local copy, conflict copies, imports) is a path dependency, unchanged. The root workspace now `exclude`s `apps/desktop` and `apps/mobile`: without it Cargo resolves the desktop crates' `workspace = true` fields against the root workspace and fails. Side effects: the server sees the desktop's `OctaPass-Desktop/…` user agent (the device is `platform: "cli"`), and the CLI pulls in the desktop's device-unlock crate (Touch ID/Windows Hello/polkit code it doesn't call).
  - **Session = the desktop's device unlock with the keyring as the device lock.** `unlock` enrols a random 32-byte secret in the OS keyring (`keyring` 4: Keychain, Credential Manager, Secret Service; service "Octa Pass CLI", entry named by `account_tag`), and the core wraps the account key with it into `state.json`. The keyring entry also holds the idle deadline (default 30 minutes, 1 minute to 24 hours, moved forward on every use); an expired entry is deleted and the wrapped key dropped. `lock` deletes both. The 14-day master password rule applies. Without a keyring (or with `OCTAPASS_NO_KEYRING=1`) nothing is kept and every command asks for the password. This keeps the ASK out of plain files and out of the keyring alike; neither half opens the vault alone.
  - **One command at a time.** Each process refreshes the access token from the stored, rotating refresh token, so concurrent processes would present the same token and the server would revoke the session. Commands take an exclusive lock on `<data dir>/cli.lock`; `run` releases it before starting its command. The runtime is single-threaded and yields before syncing, so the refresh started by unlocking always finishes before the process exits.
  - **Script contract:** exit codes 0–8 (documented, never renumbered), `--json`, `--password-stdin`, messages on stderr, no colours. Secrets reach stdout only from `get --field`, `get --json`, `read`, `export` and `reset-master-password` (the new Recovery Kit), with a warning when stdout is a terminal. `export` always asks for the master password again. `run` resolves whole-value references only and replaces itself with the command on Unix (`exec`), so signals and exit codes are the command's own.
  - **Not done then, all built since** (see the 2026-11-02 entry): the desktop app's session over IPC, item editing and sign-up from the CLI, output masking in `run`, CXF and encrypted export, real vault names. The real OS keyrings aren't exercised by the tests (they use an in-memory store through `octapass_cli::Context`).

- 2026-10-27 (branch `m19-master-password`): the CLI has `change-master-password` and `reset-master-password`. A change needs the vault signed in and unlocked, asks for the current password again (the server's OPAQUE reauth) and a new one twice; the vault drops the keyring session and the CLI enrols a new one, as device unlock has to be turned on again.
