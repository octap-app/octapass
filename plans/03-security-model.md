# 03 — Security model

This is the most important plan. Every other plan depends on it. Changes to it need a recorded decision and, after 1.0, an external review.

## Goals

1. **Confidentiality against the server.** Someone with full access to our servers and database, including us, a hacker or a court order, can't read vault contents or the master password.
2. **Resistance to offline cracking.** A stolen database can't be brute-forced, even for weak master passwords.
3. **Integrity.** The server can't swap, roll back or forge items without clients detecting it (P1: full rollback detection).
4. **Recoverability without a backdoor.** Users who forget their password can recover using something only they hold.
5. **Phishing-safe autofill.** Credentials go only to the site they belong to, and only when the user asks.

## Primitives

| Purpose | Algorithm | Crate |
|---|---|---|
| Password KDF | Argon2id, m = 64 MiB, t = 3, p = 1 (parameters stored per account, upgradable) | `argon2` |
| Key derivation | HKDF-SHA256 with distinct `info` labels per purpose | `hkdf`, `sha2` |
| Symmetric encryption | XChaCha20-Poly1305 (random 192-bit nonce), with associated data | `chacha20poly1305` |
| Public-key encryption (sharing) | Hybrid X25519 + ML-KEM-768 sealed box (HKDF + XChaCha20-Poly1305). The X25519-only box still opens, and is used for accounts with no ML-KEM key yet | `x25519-dalek`, `ml-kem` |
| Signatures | Ed25519 | `ed25519-dalek` |
| Key log | RFC 9162 Merkle tree (SHA-256), RFC 9497 VOPRF labels (ristretto255-SHA512) | `sha2`, `voprf` |
| Password-authenticated login | OPAQUE (RFC 9807), ristretto255 + Argon2id | `opaque-ke` |
| Passkeys | ES256 (P-256), EdDSA | `p256`, `ed25519-dalek` |
| Randomness | OS CSPRNG (`getrandom`; `crypto.getRandomValues` in WASM) | `rand_core` |
| Memory hygiene | `zeroize` on all key material; `secrecy` wrappers | `zeroize`, `secrecy` |

`p = 1` because WASM runs Argon2 lanes one after another. `p = 4` would make browser unlock 4× slower for no security gain there.

## Key hierarchy

```
 master password ──NFKD──► Argon2id(salt = HKDF(account_salt, email)) ──► pw_key ─┐
                                                                                  ├─► HKDF ──► AUK  (Account Unlock Key)
 Secret Key (128-bit, generated on device, never sent) ──► HKDF(salt = account_salt) ► sk_key ─┘        └─► auth_secret ──► OPAQUE
                                                                                         
 AUK ──unwraps──► ASK (Account Symmetric Key, random 256-bit)
 ASK ──unwraps──► account private keys (X25519 encryption, Ed25519 signing, ML-KEM-768 encryption)
 ASK ──unwraps──► personal Vault Keys
 member X25519 private key ──opens──► shared Vault Keys (sealed to each member, signed by sharer)
 Vault Key ──unwraps──► Item Keys (random per item)
 Item Key ──decrypts──► item overview (title, URLs, icon hint) and item details (everything else)
 Item Key ──unwraps──► File Keys (random per attachment; wrapped key, name, type and size in the details)
 File Key ──decrypts──► the attachment's file, in 64 KiB XChaCha20-Poly1305 chunks (STREAM)

 Recovery Key (256-bit, shown once) ──wraps──► ASK  (stored server-side as recovery_wrapped_ask)
 Device Key (hardware-backed, biometric-gated) ──wraps──► ASK (stored only on that device)
```

- **Secret Key** format: `OP1-XXXXXX-XXXXXX-XXXXX-XXXXX-XXXXX-XXXXXX` (version + 128 random bits, Crockford base32). It's stored on each signed-in device and in the Recovery Kit. New devices need it once, by typing it, scanning the kit's QR code, or approving from an existing device.
- **Why both a password and a Secret Key:** a database leak gives the attacker OPAQUE records and wrapped keys, but cracking them needs the Secret Key too. 128 random bits can't be brute-forced, so even `password123` users are protected against server breaches. (1Password uses the same approach.)
- **Item keys** let a single item be shared or re-encrypted without touching the rest of the vault.
- **Associated data** on every ciphertext binds it to `(account_id | vault_id | item_id | field_group | schema_version)`. The server can't move an encrypted password from one item into another.
- **Ciphertext envelope:** `version(1) ‖ key_id(16) ‖ nonce(24) ‖ ciphertext ‖ tag(16)`, base64url in JSON.

## Authentication to the server

1. **Sign-up:** the client generates the Secret Key, account salt, ASK, keypairs and Recovery Key. It runs OPAQUE registration with `auth_secret`. It uploads the OPAQUE record, the wrapped ASK, the wrapped private keys, public keys, and `recovery_wrapped_ask`. The email is verified with a 6-digit code.
2. **Login:** OPAQUE login gives both sides a session key without the server ever seeing `auth_secret`. The server issues a 15-minute access token plus a refresh token bound to a per-device Ed25519 key (each refresh request is signed).
3. **New device:** needs email + password + Secret Key, plus the account's 2FA if enabled (TOTP or WebAuthn). A "new sign-in" email is sent (device name, platform and time; no IP geolocation).
4. **Account 2FA** ("two-step sign-in" in the apps) protects *access to the ciphertext*. It isn't part of the encryption. It's asked after OPAQUE succeeds, so a wrong password never reveals whether it's on. Methods: TOTP (required to turn it on), WebAuthn security keys (optional extra; web vault only, because keys are bound to the web vault's RP ID), 10 single-use recovery codes. A device that finished signing in gets a trusted-device token that skips the step while the device stays in the device list (at most 30 days). Every change needs a fresh reauth (purpose `two-step`).
5. **Rate limiting:** per account and per IP, exponential backoff, and CAPTCHA-free proof-of-work after repeated failures.

## Unlocking on a device

| Method | How |
|---|---|
| Master password | Re-derive AUK → unwrap ASK. Always available. |
| Device unlock (iOS/macOS) | ASK wrapped by a Secure Enclave key with access control `[.biometryCurrentSet, .or, .devicePasscode]`: Face ID / Touch ID, or the device passcode (Mac: login password) when biometrics are unavailable or fail. Enrolling a new face/fingerprint invalidates the biometric path. |
| Device unlock (Android) | Android Keystore key (StrongBox when available) with `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`, unlocked through `BiometricPrompt` allowing the fingerprint/face **or** the screen-lock PIN, pattern or password. Android 9–10 fall back to `KeyguardManager` for the device credential. |
| Device unlock (Windows) | `KeyCredentialManager` key (TPM-backed) wraps ASK. Windows Hello verifies the face, fingerprint **or the Windows Hello PIN**, so machines without biometric hardware still get quick unlock. |
| Device unlock (Linux) | Through polkit, which asks for the user's system password (or fingerprint via fprintd where set up), releasing an ASK copy kept in the system keyring. Otherwise the master password. |
| CLI | Master password, **or** the running desktop app, which confirms with the device lock (History, 2026-11-02). Between commands, `octapass unlock` keeps a session: ASK wrapped (device-unlock derivation) by a random 32-byte secret kept in the OS keyring with no user-presence check, together with an idle deadline (default 30 minutes, at most 24 hours). Expired or `octapass lock`ed, the secret is deleted. Without a keyring, the master password every time (plan 05 History). |
| Browser extension and web vault | Master password, **or** a device passkey with the WebAuthn **PRF** extension: the browser asks for Touch ID / Face ID / fingerprint / Windows Hello / the device PIN or password, and the PRF output unwraps ASK (web vault in M1, see plan 11), **or** unlock through the desktop app over native messaging. |
| **Stay unlocked** (plan 18; on by default in the apps and the extension, never in the web vault or the CLI) | ASK wrapped (device-unlock derivation) by a random 32-byte secret kept where **the device's own lock guards it but nothing asks for it**: iOS a Keychain item with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` and no access-control flags, in the app group the AutoFill extension shares; Android a Keystore key (StrongBox where available) with `setUnlockedDeviceRequired(true)` and no user-authentication requirement; macOS a Keychain item with no access-control flags (`AfterFirstUnlockThisDeviceOnly`); Windows DPAPI, user scope; Linux the Secret Service. The browser extension holds nothing on disk: it gets ASK from the desktop app over native messaging with no prompt while the app stays unlocked, and otherwise keeps its session in memory until the browser closes. The CLI's `octapass unlock` session is the model. |

Locking zeroes ASK and every derived key in memory, and closes the decrypted search index.

With stay unlocked on, nothing locks by time or with the computer: the vault locks on **Lock now** (which then holds until the user unlocks), when the 14-day check comes due, and when the app or browser ends; the next start opens it again without a prompt.

### Device unlock rules

Quick unlock always uses **the device's own lock**: biometrics when available, otherwise the device passcode, PIN or password. The operating system enforces attempt limits and lockouts in hardware (Secure Enclave, Keystore, TPM, the authenticator for passkeys), so Octa Pass doesn't add a separate PIN that would be weaker and one more secret to remember.

- Device unlock can only be turned on after unlocking with the master password. It's per device and never synced.
- A full master password unlock is required every **14 days**, after an app update that changes the key format, and after a master password change, key rotation or "sign out other devices". Those events delete the device-unlock key **and the stay-unlocked key** (plan 18); the 14-day check stops stay unlocked until the master password is typed once.
- Devices without any screen lock can't use device unlock. They follow the lockless parity rule below: no prompt while the vault is already unlocked, and the master password after a restart or lock.
- Order on the unlock screen: the device unlock prompt opens automatically when its gate is on, with **Use master password** always visible.
- With stay unlocked on (plan 18), its key opens the vault before any prompt; the unlock screen, and its automatic device prompt, appear only when it can't (switch off, no key yet, "Lock now" holding, the 14-day check due).

### Two device-auth gates

Two independent **per-device** settings, both on by default, **never synced** (2026-10-27 decision; revision of the earlier "Fill without unlocking" opt-in). **They apply only while stay unlocked (plan 18, below) is off**: Settings shows them under its switch, greyed out while it's on, and they keep their values for when it's turned off.

1. **App/extension open** — where the OS provides a lock, opening Octa Pass asks for it, whatever the autofill setting says. Turning the gate off makes opening ask for the master password instead.
2. **Autofill** — on: every fill asks for the device lock. Off: filling works directly **while the vault is unlocked**. A locked vault always asks at least once, and the settings show a plain warning when this is off.

- **An open vault doesn't ask to reveal or copy; export and the account always ask** (2026-11-06, maintainer decision, History; replaces "Reveal and copy ask once per unlock", 2026-11-05). While the vault is unlocked in this app or extension, revealing and copying (fields, QR codes, SSH keys, environment values) never ask, however it was unlocked: the device lock, the master password, stay unlocked, the open gate off, a lockless device. Export, saving a secret to a file, the Secret Key, the Recovery Kit and recovery code, master password change and reset, key rotation and account deletion ask every time, however the vault was unlocked. Asking is device auth where available, the master password otherwise; neither switch relaxes it.
- **Lockless devices follow Google Password Manager**: with no OS credential there is nothing to verify with, so opening an already-unlocked vault and filling don't prompt. After a restart or a lock, the master password opens the vault. This is stated plainly in Settings. There is no separate "fill without unlocking" opt-in. The one long-lived key copy kept without a prompt is stay unlocked's (below), and it is guarded by the device's own lock, so a lockless device can't stay unlocked.
- **The web vault is never gateless**: a web page can't tell who is at the keyboard, so every unlock there is the master password or a device passkey.
- **Extension device auth is mandatory**: the in-extension WebAuthn PRF passkey is the primary path, with the desktop app over native messaging as a fallback, then the master password. It works with no account and no desktop app, offline. The PRF output unwraps ASK only in the service worker. The passkey needs a browser that lets the extension make one for itself (Chrome and Edge: RP ID = the extension ID). Firefox doesn't: its extension WebAuthn (150+) only accepts an RP ID the extension has host permissions for, never the extension's own origin, so in Firefox the desktop app is the path (History 2026-11-04).

### Stay unlocked while logged in (plan 18)

**Decision (maintainer, 2026-11-05), built 2026-11-05:** a per-device setting, **"Stay unlocked while you're logged in to this device"**, **on by default**, never synced. A logged-in, unlocked device opens Octa Pass unlocked with no prompt, the way Chrome's saved passwords work, and filling doesn't ask.

- **The key.** The device-unlock wrapping of ASK under a random 32-byte secret kept where the device's own lock guards it but nothing asks for it (the table above). It's per account, and deleted by the events that delete the device-unlock key: a master password change or reset, a Secret Key rotation, and forgetting the account (sign-out, a new store for it). "Sign out other devices" only happens through those here, and there is no key-format update yet; one must delete it the same way. Turning the switch off deletes it.
- **It needs a device lock.** No passcode (iOS), no secure lock screen (Android) or no running keyring (Linux) means it can't stay unlocked: the device falls back to the lock timer and the two gates, and Settings says why. iOS deletes the item itself when the passcode is removed; a key found without a passcode is deleted unused.
- **What stays the same.** The 14-day master password check stops it until the password is typed once. **Reveal and copy don't ask** while the vault is open (the rule above, 2026-11-06). **The high-risk actions ask every time**: export, saving a secret to a file, the Secret Key, the Recovery Kit and recovery code, master password change and reset, key rotation, account deletion.
- **Lock now holds.** After the user's own "Lock now", the vault stays locked until the user unlocks it, or the app or browser restarts.
- **The browser extension.** With the desktop app staying unlocked, the extension opens through it over native messaging at browser start and when its lock screen shows, with no prompt (the app skips its device-lock check for `get-session-key-wrap` while it stays unlocked and is unlocked to the same account). On its own, the extension keeps the vault in memory (`chrome.storage.session`) until the browser closes, with no idle timer and no lock on system lock; a computer lock or sleep only resets the reveal state. After a browser restart, one normal unlock.
- **Not in the web vault** (a page can't tell who is at the keyboard) **or the CLI** (its `octapass unlock` session already works this way, with an idle deadline).

### Local mode keys

A local vault has no server, so there is no OPAQUE login and no Secret Key on a server to defend against. The threat is different: someone **copying the vault file off the device** and guessing the master password offline (the KeePass threat model).

```
master password ──NFKD──► Argon2id(local_salt; m = 256 MiB where the device allows, else 64 MiB; t = 3) ──► pw_key ─┐
device chip key (Secure Enclave / Keystore / TPM; non-exportable) ──► hw_secret ─────────────────────────────────┤
                                                                                                                 └─► HKDF ──► LUK (Local Unlock Key) ──unwraps──► ASK
```

- The rest of the hierarchy (ASK → vault key → item keys, envelopes, AAD) is **identical** to synced accounts, so "Turn on sync" only re-wraps the ASK.
- `hw_secret` binds the vault to the device chip where one exists, so a copied file is useless elsewhere. Where there's no chip (some Linux machines, the browser extension without the desktop app), the master password must be **strong**: zxcvbn score 4 required, and the UI explains why.
- Device unlock (Face ID / Windows Hello / passcode) works exactly as for accounts.
- **Backup files** are encrypted with a key derived from the master password only (no device chip, or they couldn't be restored on another device): `Argon2id(256 MiB, t = 4)` over the master password + a random backup salt, XChaCha20-Poly1305 over the whole vault, and an authenticated header with the format version. They're as strong as the master password, which is why local mode requires a strong one.
- **Recovery:** there is no server-side recovery code. The local Recovery Kit holds a **backup recovery code** that can decrypt backup files if the master password is forgotten (it wraps the backup key). Losing the device, the backups and the kit means the data is gone. This is said plainly at setup.
- **Turn on sync:** generates a Secret Key, derives the account AUK, re-wraps the ASK, registers with OPAQUE, uploads the items (already encrypted), then deletes the local-only wrapping. No item is decrypted or re-encrypted.

### Saving while locked

**Decision (maintainer, 2026-11-05): saving or adding must not require unlocking.** A login (and, in the browser extension, an address, card or API key) the user saves while Octa Pass is locked goes into a **save inbox** on that device, and is merged into the vault at the next unlock. Built in the core (`octapass_core::inbox`), the browser and Safari extensions, and the Android Autofill service. iOS gives AutoFill extensions no save request, so there is nothing to save there; the desktop app has no save prompts of its own.

- **Sealed to the account's own public keys.** The vault key only exists after an unlock, so a locked device can't encrypt into the vault. Each entry gets a random 32-byte entry key; the entry JSON is an envelope under it (context `inbox-entry:{owner}:{entryId}`), and the entry key is sealed with the **hybrid X25519 + ML-KEM-768 sealed box** sharing uses (`sharing::seal`, context `inbox:{owner}`). `owner` is the account id, or a local vault's personal vault id. No new primitive: the sealed box and the envelope as they are.
- **The key is pinned at unlock, from the private keys.** Every unlock writes an **inbox key** next to the inbox: the X25519 public key computed from the account's private key, and the account's ML-KEM public key (checked against the signed key record at unlock, as sharing does). It is never taken from an account bundle the server sent, which a later sign-in can replace without the private keys checking it. An account with no ML-KEM key yet, and every **local vault** (which has an X25519 pair but no ML-KEM key), use an ML-KEM key derived from the ASK: `seed = HKDF-SHA256(ikm = ASK, salt = "", info = "octapass/v1/inbox-pq")`, 64 bytes. Nothing new is stored for it, and opening tries both keys, so entries sealed before an account got its own ML-KEM key still open. A key pinned for another vault, a malformed key and a low-order X25519 key are refused; with no key pinned (no unlock on this device since this shipped) there is nothing to save to, and the client falls back to what it did before (the extension doesn't offer; Android asks to unlock).
- **Confidentiality is unchanged.** The device seals with public keys only. It can't read an entry back while locked: only the private keys, which need an unlock, open it. The inbox holds no key that opens anything else, and its readable parts are entry ids and the public inbox key. It stays on the device (extension IndexedDB `octapass-inbox`; on Android `<store>.inbox` beside the shared store, under the store's file lock) and **never syncs**; sign-out deletes it on Android, and in the extension it can only ever be opened by the same account.
- **The new integrity point: entries are marked for review.** Someone holding the device while it's locked can now add entries they can't read, and so can a page script that fills and submits a form. That's why a **new** item from the inbox is tagged `Unconfirmed` (plan 05's draft mark), so it shows for review. An entry for a login that already has the site and username **updates** its password, the old one going into the password history, and **never adds or removes the review mark**: a confirmed login stays confirmed (the rule for a suggested-password draft on a confirmed login), an unconfirmed one stays unconfirmed. Nothing is ever deleted or demoted because of an entry. Exact duplicates (the password the login already has, a repeat of a newer entry, or a login for another part of the site with the same username and password) are dropped quietly. Several entries for one login apply oldest first, so the newest is current and the others are in the history.
- **Cap: 50 entries**, each at most 16 KiB of JSON. A full inbox refuses new entries rather than dropping old ones, so a flood can't push out what the user saved, and nothing more is offered until an unlock empties it.
- **Merging.** Every unlock pins the key, opens every entry, merges, and removes what merged or was a duplicate. An entry whose merge fails (offline engine error, a read-only vault) stays for the next unlock. An entry that can't be opened (sealed to a key that isn't this vault's, or damaged) is removed: it never will open.
- **Locked prompts** can't compare with the vault, so they always ask "Save" (never "Update", never silent because it's already saved), with a line saying it's added at the next unlock. The never-save list is outside the vault and still applies. There is no locked lookup list of saved sites (maintainer, 2026-11-05: not wanted).

## Post-quantum sharing

**Status: built, not audited. Needs the external cryptographer review named in plan 09's risks table before anyone relies on it.**

Everything symmetric is already 256-bit. The one exposure to a future quantum computer is that a key sealed with X25519 today could be recorded and opened later, so sealing gets a hybrid box: it stays safe as long as **either** X25519 **or** ML-KEM-768 holds. There is never an ML-KEM-only mode.

```
ss_x       = X25519(ephemeral_secret, recipient_x25519_public)     low-order keys refused
ct_m, ss_m = ML-KEM-768.Encaps(recipient_mlkem_public)             FIPS 203
transcript = SHA-256("octapass/v2/seal-transcript" ‖ 0x00 ‖ ephemeral_public ‖ recipient_x25519_public ‖ ct_m ‖ recipient_mlkem_public)
wrap_key   = HKDF-SHA256(ikm = ss_m ‖ ss_x, salt = transcript, info = "octapass/v2/seal")
sealed     = 0x02 ‖ ephemeral_public (32) ‖ ct_m (1088) ‖ nonce (24) ‖ XChaCha20-Poly1305(wrap_key, key, aad = "octapass/v1|" + context)
```

The secrets are concatenated in the order X25519MLKEM768 uses, and the salt binds both public keys and both ciphertexts, so neither half can be replayed into another box. Every sealed key is 1,193 bytes; the X25519 box stays 105.

- **Versioned.** The first byte picks the construction. `0x01` boxes keep opening for good, so every existing grant and emergency key keeps working.
- **The ML-KEM key.** Each account gets one ML-KEM-768 key pair. Its private part is the 64-byte FIPS 203 seed (`d ‖ z`), in the new `wrappedPqPrivateKey`, sealed by the ASK with context `pqprivkey`. It sits apart from `wrappedPrivateKeys`, so a client that doesn't know about it still unlocks. The key is random, never derived from the X25519 key, which a quantum attacker would have.
- **The public key can't be swapped silently.** The public key travels only inside the signed key record below. Clients seal to it only if the record verifies against the account's Ed25519 key, so the existing fingerprint (which covers that Ed25519 key) also covers the ML-KEM key, and existing "verified" marks stay valid.
- **Upgrading.** No sign-up change: every signed-in client, on unlock, generates the key and publishes the record if the account has none. Two devices racing is settled by the server (first one wins, the other adopts its key from `GET /v1/account`).
- **Which box a client uses.** Hybrid when the recipient has a valid key record, X25519 when they have none. That fallback is why a server could try to hide someone's ML-KEM key: a device that has seen a record for an account refuses to go back, and the key log records it for everyone else.
- **Old grants** stay `0x01` until the vault's next key rotation reseals them. Harvested copies of those keep the classical exposure. Emergency keys stay as sealed until the grantor adds the contact again. Stated in the docs.

## Key transparency

**Status: built, not audited. Needs the external cryptographer review named in plan 09's risks table before anyone relies on it. It supports the fingerprint check and does not replace it.**

A sharer gets a member's public keys from the server. A malicious server could hand out its own keys and read what is sealed. Fingerprints catch that, but only for people who compare them. The key log makes a swap **visible to the key's real owner** without anyone comparing anything: the server can't show Alice a key for `bob@example.com` without putting it in an append-only log that Bob's devices read.

**Key record.** A statement an account makes about itself, signed by its Ed25519 key:

```
message     = "octapass/v1/key-record" ‖ 0x00 ‖ for each field: len (u32 BE) ‖ UTF-8 bytes
fields      = logId, accountId, label, publicEncKey, publicSignKey, publicPqKey, createdAt (decimal ms)
record_hash = SHA-256("octapass/v1/key-record-hash" ‖ 0x00 ‖ message ‖ signature)
```

**The log.** One RFC 9162 Merkle tree per server (`SHA-256(0x00 ‖ leaf)`, `SHA-256(0x01 ‖ left ‖ right)`), with `leaf = label (32) ‖ record_hash (32)`. Only hashes are in the tree. Records live beside it and are deleted with the account; the leaf stays, and is meaningless without the record. Account public keys never change in this model (a Secret Key or password change doesn't touch them), so a healthy account has **one** leaf.

**Signed heads.** `Ed25519(log_key, "octapass/v1/key-log-head" ‖ 0x00 ‖ logId ‖ size (u64 BE) ‖ timestamp ms (u64 BE) ‖ root)`, where `logId = SHA-256("octapass/v1/key-log-id" ‖ 0x00 ‖ log_public_key ‖ oprf_public_key)`. Both log keys derive from the server secret, so they stay with a backup of the data directory; losing that secret starts a new log, which clients report.

**Labels keep emails private.** The log has to be findable by email, or the server could file a fake key under a label Bob never looks at. But a plain hash would let any signed-in user test a list of emails offline, undoing the enumeration limits in plan 15. So `label = SHA-256("octapass/v1/key-log-label" ‖ 0x00 ‖ VOPRF(oprf_key, normalised_email))`, with the RFC 9497 VOPRF (ristretto255-SHA512) already in our dependency tree through `opaque-ke`. Asking for a label is an online request, charged to its own per-account budget, and its proof shows the server used the one key clients pinned, so it can't give Alice and Bob different labels for one email.

**What clients check.**

1. **Heads.** Each device pins the log's two public keys and the newest head it has seen. A new head must be correctly signed, not older, not more than 7 days old, and proven by an RFC 9162 consistency proof to extend the pinned one. A device's first pin comes from the server, unless its account already has a record, whose signed `logId` settles it.
2. **Other people's keys.** Before sealing, the client gets the record for the account's label with an inclusion proof, and checks signature, account id, keys, label and log id all match what the server offered. A failure **refuses to seal**.
3. **Its own keys (monitoring).** After unlock, at most hourly, each device checks its own record, then reads every leaf added since (64 bytes each), rebuilds the Merkle root from them so nothing can be left out, and looks for any leaf under its own label that isn't its own record. One is an alert to the user that a key was published for their email which they didn't make. Scanning starts at the account's own leaf: anything earlier belongs to before the account existed.

**Fingerprints stay.** The log is shown beside them. A member is "in the key log", "not in the key log yet" or "key log check failed".

**What it doesn't do, stated plainly.**

- **Split views.** A server that shows Alice one log and Bob another isn't caught by either of them alone. Their devices each see a consistent history. Heads are signed, so two heads that disagree are proof of misbehaviour, but something has to compare them. Fixing this needs **independent witnesses** that cosign heads, and nobody has decided who runs those (see plan 09 and the decisions in History). Until then, comparing fingerprints is the only check against a server willing to fork its log.
- **"Not in the log yet".** Until an account's client publishes, there's nothing to check, and a server could claim that of any account a device hasn't seen before. So this shows as a warning, not a pass. A proof of absence needs a map structure this design leaves out.
- **Freshness.** Inclusion shows a record was logged, not that it's the newest. It holds while account keys never change, and devices refuse to step back to an older leaf for a contact they've seen.
- **The granter's key on an incoming grant** comes from the server. The members screen checks each member against the log, but opening a vault doesn't.
- **Monitoring needs a device.** Nothing is watching while none of the owner's devices is online. Cost grows with the log (about 640 KB per 10,000 new accounts).

## Organisations and single sign-on

Teams build on shared vaults (plan 15) and add **no new key and no new way to reach one**. Decisions (2026-11-02, branch `m25-teams`):

1. **No organisation key.** An organisation's roles (`owner`, `admin`, `member`) live on the server and give no cryptographic access. Being an admin opens nothing. There is no key an admin or the server could use to read a member's vault, and no admin reset of a master password.
2. **An organisation vault is a shared vault with an `orgId`.** It has the same random Vault Key, sealed to each member and signed by the granter, verified by the recipient exactly as in plan 15. Clients need no new crypto to open one.
3. **Groups are lists of people, not key holders.** Linking a group to a vault says who *should* have it. Only a device that already holds the Vault Key can act on that, by sealing a grant to each new person. There are no group keys. Adding someone to a group gives them nothing until a key holder applies it.
4. **Applying access is always reviewed by a person.** The list of who should get a key comes from the server, so a device must never seal to it blindly: a malicious server could add itself. The client shows every person, their role and their locally computed fingerprint, and seals only after the key holder confirms. This is the same trust as typing an email into the sharing screen, and the same out-of-band fingerprint check applies. The server also accepts a grant only for someone the organisation entitles, with exactly that role.
5. **Taking access away doesn't wait for a key holder.** Leaving a group, losing a vault link or leaving the organisation stops the server serving that vault at once. The vault is marked for rotation, and the next key holder rotates it as plan 15 describes. A lowered role also removes access at once, until a new grant with the lower role is applied, because a role is part of the signed grant and the server can't rewrite one.
6. **Organisation owners are entitled to every organisation vault, as vault owners.** Otherwise a departing employee who was the only key holder would take the vault with them. Members are told this before they join. It reaches only organisation vaults, never a personal vault, and it works by ordinary reviewed grants: the server can't do it alone. A vault with no key holder left is unreadable by anyone, and can only be deleted.
7. **Policies restrict; they never move a key.** No policy makes a client send, seal or weaken a key. Policies the server can enforce are enforced there (two-step sign-in, SSO, share links, emergency access). Those only a client can apply (master password length, auto-lock, leaving organisation vaults out of exports) are labelled as client-side wherever they're shown, because a modified client can ignore them. The server never sees a master password, so it can't check one.
8. **A policy can never reach a personal vault's contents.** Withholding organisation vaults from a member who breaks the two-step policy stops ciphertext being served, like two-step sign-in itself. It does not touch their personal vault, and a member can always leave (the last owner first hands the organisation on, or deletes it).

### SSO is sign-in only

**SSO unlock is not offered, because it can't be zero-knowledge.** An identity provider's answer is a statement, not a secret. Anyone who runs or breaks into the provider can produce that statement, and any key released on the strength of it reaches them too. The designs on offer move the problem rather than solve it: a key connector or escrow service holds the key for the organisation, and a key derived from an IdP claim belongs to whoever can mint the claim. Neither survives goal 1. Device-held keys approved from another device are zero-knowledge, but that is the device unlock above, not SSO.

So **the master password and Secret Key stay the only way to derive the AUK**, on every platform, for every member, and device unlock works as before. SSO decides only whether a sign-in may proceed:

- **It adds a step and never replaces one.** OPAQUE runs first and must succeed. Neither the IdP nor the server can start a session without it, and SSO adds nothing to any key derivation. The worst a hostile IdP can do is refuse sign-ins or wave one through that already had the master password and Secret Key.
- **It runs after the password.** Nothing about SSO shows before OPAQUE succeeds, so it reveals nothing about which accounts exist or belong to an organisation.
- **The flow:** `login/finish` answers `401 sso-required` with a challenge id (kept by the client) and a separate browser URL. The server is the OpenID Connect relying party (authorization code flow with PKCE, `state` and `nonce`). After the IdP, the browser page shows a 6-digit code, which the user types into the app. That code binds the browser to the device: someone who stole a master password and Secret Key and sends the victim the link gets nothing, because the code appears only on the victim's screen, next to the device name and platform, with a warning. Five wrong codes end the sign-in.
- **The ID token** comes straight from the token endpoint over TLS, with the client's own authentication and PKCE, so its issuer is established by TLS as OpenID Connect Core 3.1.3.7 allows. `iss`, `aud`, `azp`, `exp`, `iat` and `nonce` are checked, and `alg: none` is refused. No JWKS or RSA code is added to the server (plan 03 History, 2026-10-24, avoids the `rsa` crate). Only OpenID Connect is built. SAML is not: its XML signature handling is a well-known source of authentication bypasses, and every mainstream IdP also speaks OIDC.
- **Identity:** the first SSO sign-in links `(issuer, sub)` to the member when the token's `email` equals the account email and isn't marked unverified. After that the link decides. A link only ever satisfies this step for that account. Membership is opt-in, so an organisation can't apply SSO to an account by claiming an email domain.
- **Owners are exempt,** so a broken IdP can't lock an organisation out. `requireSso` can't be turned on until an owner has completed a test sign-in with the current settings.
- **Freshness:** each session records when SSO last passed. Once that's older than `ssoMaxAgeHours` (default 168), the refresh fails and the device signs in again, so disabling someone in the IdP takes effect within that time. Removing them from the organisation takes effect at once.
- **The OIDC client secret** is sealed under the server secret like an authenticator secret (AAD = organisation id). The server can read it by design. It opens the IdP's token endpoint, never a vault.
- **SSRF:** the issuer is admin-supplied, so the server fetches it the way it fetches icons: HTTPS only, public addresses only, no redirects, small bodies, short timeouts. Private addresses are allowed only with `OCTAPASS_SSO_PRIVATE_NETWORK=on`, for self-hosters with an IdP on their own network. Plain HTTP works only in dev mode.

## Non-human access

Plan 16 adds two ways for software to get secrets. Neither lets the server read anything, and neither adds a second way to decrypt: both end at the key hierarchy above.

### Service accounts

A service account lets a CI job or a server read **one shared vault** with no person present. It's a vault member that isn't a person: it holds a key pair, and the vault key is sealed to it exactly as to any member.

```
token root (256-bit, random, generated on the creator's device, never sent to the server)
 ├─ HKDF(salt = service account id, info = "octapass/v1/service-account/encryption") ► X25519 private key
 └─ HKDF(salt = service account id, info = "octapass/v1/service-account/signing")    ► Ed25519 signing key

 X25519 key ──opens──► the vault key, from a signed grant (the same `SignedGrant` members get,
                       recipient = the service account id, context `vaultkey:<vault>:<serviceAccountId>`)
 vault key ──unwraps──► item keys ──decrypt──► items, on the runner
```

- **The token is the key.** `opsa1_…` is base64url of `version ‖ service account id ‖ vault id ‖ root ‖ pinned public signing key ‖ server URL ‖ checksum`. It's shown once, on the creator's device, and never reaches the server: the server stores the two public keys, the sealed vault key and the grant. A database breach or a compelled operator gets ciphertext, as for any member. The checksum only catches damaged copies; it isn't a security control.
- **Signing in.** The runner asks for a single-use 32-byte challenge, signs `"octapass/v1/service-account-auth" ‖ 0x00 ‖` length-prefixed `serviceAccountId, challenge` with Ed25519, and gets a 15-minute access token that only reaches `/v1/service-accounts/…`. No token material crosses the network, so TLS-terminating proxies and server logs never see it. Unknown ids get a challenge too, so ids can't be probed.
- **Decryption happens on the runner**, in the CLI's memory. Nothing is written to disk.
- **One shared vault only.** Personal and family vaults are refused: a personal vault's key can't be rotated, so it could never be taken back, and a family vault isn't the place for machines. Users make a shared vault holding only what the job needs. Creating one takes the manage role.
- **Read-only by default.** The role is signed in the grant and enforced by the server. `--write` gives the `write` role, which can save items and nothing else: no members, no grants, no rotation.
- **The grant is verified against a key pinned in the token**, the creator's public signing key, never one the server supplies. A server that swaps the sealed key or the role is caught before the vault is opened. So after a rotation by another manager the token stops working and fails closed with a plain message: the creator issues a new one. Rotations by the creator carry on working. This is a deliberate trade: an outage of one token rather than trusting a key the server names.
- **Names are ciphertext.** A service account's name is sealed under the creator's ASK (context `service-account-name:<vault>:<serviceAccountId>`), so the server sees only an id. Other managers see the id, role and dates.
- **Revoking** removes it on the server at once (a stolen token can no longer fetch ciphertext or sign in) and rotates the vault key, as removing a member does, so ciphertext fetched later isn't readable with the old key. As with members, anything already read can't be taken back, and keys a holder kept from before still open the items they could open then: **rotate the secrets themselves after a leak**. Rotations by any manager re-grant active service accounts; a client too old to do so leaves the account unable to read, which fails closed.
- **Optional expiry**, enforced by the server.
- **Security log.** Each fetch and write is logged to the creator's security log with the service account's id. Logging is by the server, so a runner can't skip it. **It logs vault reads, not which secret**: the server hands over ciphertext and can't know which item a runner decrypted, and asking the runner would be a report it could fake. A token holder who saved ciphertext can read it offline without a log entry.

### Octa Pass Connect

Connect is a helper on the user's own device, in the CLI (`octapass connect serve`) or the desktop app, that hands one secret at a time to a local tool that asks by `octapass://` reference.

- **Local only.** A Unix socket (mode `0600`, in a `0700` folder, the peer's uid checked) on macOS and Linux; `127.0.0.1` on an OS-chosen port when asked for, and on Windows. Never another interface. Loopback refuses any request with an `Origin` header or a `Host` other than the loopback address, so a website can't reach it through the browser (DNS rebinding, cross-origin requests).
- **Per-client approval.** The first request from a client opens a prompt to the person showing the name the client claims and, on a socket, the program that really connected. Names are only claims: the prompt says so. One prompt at a time, and refusing ends the request.
- **Session token.** Approval returns a random 256-bit token that the client keeps. Only its SHA-256 is stored, in a `0600` file on the device. It expires after 30 days, can be revoked at any time, and on a socket is bound to the program that was approved.
- **No keys kept.** The CLI opens the vault for each request with the keyring session and closes it, so `octapass lock`, the idle timeout, and a restart all stop Connect at once. Connect requests don't extend the idle timeout, so a polling tool can't keep the vault unlocked. The desktop app uses its unlocked vault and answers "locked" when it's locked. Connect never unlocks anything.
- **Every secret handed out is recorded, before it's handed out.** Each entry (when, which client, which reference) is sealed under the ASK (context `audit-detail:<accountId>`) into a queue on the device, then sent to the security log. The server stores a ciphertext blob plus its own timestamp: it learns *that* a secret was handed out and when, never which, nor to what. Offline, entries wait in the queue and are sent later, so nothing is handed out unrecorded. If the entry can't even be written, the secret isn't handed out. It's a record for the user, not a control: a client holding the token, like malware on an unlocked device, is outside this threat model (above).

## Recovery

| Lost | Can recover with | How |
|---|---|---|
| Master password | Recovery code | Verify email → enter recovery code → unwrap ASK → set new password (Secret Key can be rotated too). |
| Secret Key | Recovery Kit, or any signed-in device | The Kit has the key printed and as a QR code; signed-in devices can display it after unlock. |
| Password **and** Secret Key | Recovery code | Same as above, plus a new Secret Key is issued. |
| Everything | Emergency contact (P1) or family organiser (P1, opt-in) | They hold a sealed copy of your ASK and release it after the waiting period. |
| Everything, no contacts set | **Nothing** | Stated clearly at sign-up. This is the price of zero-knowledge. |

The Recovery Kit is a PDF generated **on the device**, never on the server. It contains the email, Secret Key, QR code, a blank line to write the password, and the recovery code.

## Threat model

| Threat | What the attacker gets | Mitigation |
|---|---|---|
| Database breach | Emails, OPAQUE records, ciphertext, public keys, metadata | Secret Key makes offline cracking impossible. Argon2id adds cost even if the Secret Key also leaks from a device. |
| Malicious or compelled server operator | The same as a breach, plus the ability to serve modified code | Native apps and extensions are signed and reproducible. **The web vault is the weak point**: the server serves its JS. Mitigations: SRI, reproducible builds with published hashes, a P1 extension check that verifies web vault hashes, and documentation recommending the apps for highest assurance. |
| Network attacker | Nothing useful | TLS 1.3, HSTS preload. OPAQUE keeps the password off the wire even if TLS is broken. |
| Phishing site | Nothing | Autofill only on the page's own host, a domain above it or a host below it on the same registrable domain (PSL); other parts of the domain only when the user picks them (plan 05, History 2026-11-05). Never in cross-origin iframes unless the user approves the frame's origin, user gesture required. Passkeys are bound to `rpId` by design. |
| Clickjacking against the extension UI (2025 research class) | Tricks the user into filling | In-page UI rendered in the top layer (popover/dialog), checks visibility and opacity of the target and of our own UI via `IntersectionObserver` v2, refuses to fill when the page manipulates our elements, and confirms when fills are triggered by synthetic events. |
| Malicious website script reading filled values | Values in the DOM | Fill only into the matched form, only after a gesture. TOTP and passwords are never filled on `http://` without a warning. The one exception, off by default: the extension's "Fill logins when a page opens" (plan 05, History 2026-11-06) fills a login saved for the page's exact host into a visible login form of a top-level `https://` page with no gesture, never when filling would ask first. With it on, the page's scripts can read that login before the user does anything. |
| Lost or stolen device | Encrypted local cache | Auto-lock, hardware-backed keys, remote sign-out (revokes refresh tokens; the local cache stays encrypted). With stay unlocked on, the stored key of a stolen **locked or powered-off** device gives nothing: it needs the phone unlocked (iOS, Android) or the user logged in (desktop). An app still running keeps its unlocked session in memory while the phone is locked, as it did within the lock timer before; there is now no timer to end it. |
| Someone at the unlocked device | With stay unlocked off: nothing without the device lock or the master password. With it on (the default): opening Octa Pass, filling logins, and revealing and copying secrets | Exporting, the Secret Key, the Recovery Kit and the account settings still ask for the device lock (or the master password), every time. The 14-day master password check still applies. Turning the switch off brings back the lock timer and the two gates. |
| Stolen service account token | That one vault, until revoked | The token is a key, so treat it as one: keep it in the CI system's secret store. Bound to one shared vault, read-only by default, optional expiry, every fetch in the security log. Revoking cuts server access at once and rotates the vault key; secrets already read must be rotated by the user. |
| Local program asking Connect for secrets | What the user approved it for | Socket or loopback only, per-client approval showing the real program where the OS tells us, token bound to that program, every hand-out logged. Malware running as the user is still out of scope (next row). |
| Someone holding the device while it's locked (or a page script submitting forms) | Can add entries to the save inbox; can't read them, or anything else | Entries are sealed to the account's public keys. New items from the inbox are tagged `Unconfirmed` for review; an existing login only gets a new password with the old one in its history, never a deleted or demoted item; at most 50 entries ("Saving while locked"). |
| Malware on the unlocked device | Potentially everything | Out of scope (as for every password manager). We limit exposure: clipboard auto-clear, minimal decrypted data in memory, no secrets in logs or crash reports. With stay unlocked on (plan 18), malware running as the user can open the vault as it can open Chrome's passwords, even while Octa Pass is closed; with it off, a locked vault gives it only ciphertext. Revealing and exporting still go through the device-lock prompt, which doesn't stop malware that reads memory. |
| Malicious shared-vault member | Items in that vault | Can't escalate beyond the vault. Removing a member rotates the vault key and re-encrypts item keys. |
| Hostile or breached identity provider | Can refuse sign-ins, or pass one that already had the master password and Secret Key | SSO runs after OPAQUE and takes no part in key derivation. It gives no path to a vault key. |
| Malicious organisation admin | Member lists, group names, policies | Admin roles open nothing. An admin reads only vaults they hold a grant for, and can lock a member out of organisation vaults but not read personal ones. Owners' access to organisation vaults is stated before joining. |
| Server adds a fake person to a group or organisation | A key holder's device is asked to seal to that person | Applying access always shows each person and fingerprint for a human to confirm (see above). Same trust as sharing today; key transparency narrows it further. |
| Server rollback / item swap | Old versions served as current | Associated data stops swaps. P1: signed vault manifests (Ed25519) with monotonic revision counters checked by clients. |
| Supply chain | Malicious dependency or build | Lockfiles, `cargo vet`, `cargo deny`, npm provenance, minimal dependencies in the core, two-person release approval, reproducible builds, SBOM. |
| Quantum, harvest-now-decrypt-later | Keys sealed with X25519 only: grants and emergency keys made before the hybrid box, or for accounts with no ML-KEM key yet | Symmetric layers (256-bit) are already safe. New seals are hybrid (see "Post-quantum sharing"). Old grants stay classical until the vault's next key rotation. Designed, **not yet reviewed by a cryptographer**. |
| Server swaps a public key to read a share | A key sealed to the server instead of the member | Fingerprints compared out of band, and the key log (see "Key transparency"), which puts any swap in an append-only log that the real owner's devices watch. Designed, **not yet reviewed by a cryptographer**. |

## What the server can see (published honestly in the docs)

- Account email, account creation date, plan/quota usage.
- Each account's public keys and key record, and which accounts look up which labels in the key log.
- Number of vaults and items, ciphertext sizes, modification timestamps. This includes when the hidden `usageStats` item is saved, a few seconds after the user uses items (copies, fills, opens a website): when, not which items.
- Which accounts share which vaults (needed to route keys).
- IP addresses and user agents of requests (kept 7 days for abuse prevention, then dropped).
- Whether 2FA is enabled. Device names (as the user typed them; encrypted in P1).
- With email breach alerts on (opt-in): the account's masked email aliases and the account email, in memory, for the length of each request.
- For organisations: the organisation's name, group names, who is in which group, each member's role, which groups reach which vaults, the policies, the SSO issuer and client id, each member's IdP subject, and the admin activity log. These are organisation metadata in plaintext, so members and the server can route access and enforce policy. Don't put secrets in them. Vault names and everything inside a vault stay encrypted.
- Each service account's id, vault, role, dates, public keys and sealed vault key, and when it fetched or saved (not which secrets, and not its name).
- That Octa Pass Connect handed out a secret, and when: the entry itself is a blob only the account can open.

On a server that turns on the masked email relay (off by default, not run on the hosted service), the relay also sees: each alias with its account and counters; the addresses of people who wrote to an alias (sealed under the relay's secret, so its operator can open them); and **mail in plaintext while it's forwarded**, in memory only. Vault contents are unaffected.

The server **cannot** see item titles, URLs, usernames, passwords, notes, TOTP secrets, passkeys, tags, folder names or attachment names.

## Breach checking

- **Passwords:** SHA-1 of the password → send the first 5 hex characters to the Pwned Passwords range API with `Add-Padding: true` → compare suffixes locally. The password never leaves the device, and the prefix matches ~800+ hashes. The request goes through our proxy by default so HIBP doesn't see user IPs; self-hosters can call HIBP directly.
- **Emails:** opt-in, off by default, and disclosed before it's turned on. The client sends the account email and its aliases to the server, which queries the HIBP breach API. The server keeps nothing about the addresses (History, 2026-11-02). It needs an HIBP API key on the hosted service; self-hosters bring their own, and without one the feature doesn't exist on that server.

## Security process

- Threat model reviewed every phase. A security section is required in every PR that touches `crypto`, `keys`, `auth`, `sync` or autofill.
- **External audit** of the core + server + extension before 1.0, with the report published in full.
- **Bug bounty** at public beta (start with a self-hosted policy + `security.txt`, then a platform).
- `SECURITY.md` with a PGP/age key and a 90-day coordinated disclosure policy.
- Fuzzing (`cargo fuzz`) for importers, the ciphertext parser and URL matching. Property tests for the crypto envelopes.
- Test vectors for every crypto construction, published in the docs so third-party clients can interoperate.

- 2026-10-24 (website icons, branch m13-site-icons): clients show website icons through the user's own Octa Pass server (plan 04 History), on by default with a per-device "Show website icons" switch. **Trade-off accepted:** the server learns which domains it is asked about (registrable domains only, cut down on the device), though not which account asked: requests carry no token or cookie, only the IP the rate limit needs. No third-party icon service is ever contacted, by the server or the clients. Local mode (no account) uses the default Octa Pass server, only while the switch is on. Devices cache icons (IndexedDB, keys are SHA-256 hashes), which shows someone with access to the device's files the sites in the vault even while it's locked; the cache is cleared when icons are turned off and on sign-out. The extension's in-page menu gets icon bytes from the service worker, for logins matching the page only, and draws them on a canvas in its closed shadow root, so the page sees no request, URL or item. The server re-encodes every icon as PNG, so no site-supplied bytes (SVG scripts, oversized images) reach clients.
- 2026-10-24 (account 2FA, branch m7-account-2fa): built as "two-step sign-in". Decisions:
  - **TOTP is required to turn it on**; security keys are an optional extra added afterwards. The extension (its origin), desktop and mobile apps (webviews) can't run WebAuthn for the web vault's RP ID, so TOTP guarantees every client can finish a sign-in. Security keys register and sign in on the web vault only.
  - **"New device" = no valid trusted-device token.** Every successful login returns one (stored hashed, 1 year from last use, rotated on use); devices already signed in get one on their next refresh. Logout and remote sign-out forget it. So turning 2FA on never interrupts signed-in devices, including their background re-login after a lapsed refresh token.
  - **Server-side secrets:** the TOTP secret is sealed with XChaCha20-Poly1305 under a key derived from the server secret (AAD = account id); recovery codes (50 bits each) are HMACs under the server secret; trusted-device tokens are SHA-256 hashes. TOTP steps are single use (last accepted step stored).
  - **Abuse limits:** 5 wrong second steps end a login attempt; 10 wrong ones per account (refill one per 5 minutes) pause the second step, add `two-step-locked` to the security log and email the owner (at most hourly).
  - **WebAuthn:** attestation `none`, ES256 and Ed25519 only (no RSA: avoids the `rsa` crate), user verification `discouraged` (the password already ran), signature counter checked. Implemented in the server (`apps/server/src/two_step/webauthn.rs`) on `p256`, `ed25519-dalek` and `ciborium`, not `webauthn-rs` (OpenSSL).
  - Self-hosters can turn it off for a locked-out user with `octapass-server admin reset-two-step <email>`.
  - **Clients:** the web vault offers security keys when `location.hostname` is the RP ID or a subdomain of it; the extension popup, desktop and mobile apps offer TOTP and recovery codes only. The trusted-device token is kept next to the Secret Key on each device and dropped on sign-out. If a background re-login (expired refresh token) is asked for the second step, the app signs out locally and the user signs in again. The extension keeps a waiting sign-in in its background worker so the popup can be closed to read a code and reopened. `octapass-ffi` got an additive API (`log_in_trusted`, `SecondFactorLogin`); the old `log_in` fails with `second-factor-required` on accounts with it on. The committed Swift/Kotlin bindings in `apps/mobile/bindings` were not regenerated (they were already behind the FFI).
- 2026-10-24 (account 2FA fixes after an independent security review):
  - **Trust can't outlive its device.** `trusted_devices.device_id` now references `devices` with `ON DELETE CASCADE` (migration 0007), trust is valid only for a non-revoked device, and tokens last at most 30 days. Before, a device could log in once while 2FA was off, let its session lapse (vanishing from the device list) and keep skipping the second step for a year. Refresh no longer issues trust, so forgetting can't be undone by a refresh. In practice trust now lasts about as long as the session: a device signing in again after 30 idle days asks for the second step (the apps sign out locally and the user signs in again).
  - **Forgetting trust:** turning two-step on forgets every device except the caller; admin `reset-two-step` and a reused refresh token forget all; `DELETE /v1/account/two-step/trusted-devices` (Settings → "Ask again" in the web vault) forgets all but the caller, logged as `trusted-devices-forgotten`.
  - **Lockout can't be raced:** each second-step try takes a token from the account's budget before it's checked (refunded on success), instead of peeking first and charging after the database work.
  - **Single use under concurrency:** a trusted-device token is consumed with a conditional delete inside the login transaction; a security-key setup is used once even with two concurrent answers.
  - **No burnt codes:** the TOTP step, recovery code or key counter is used in the same transaction that creates the session, so a failure afterwards leaves the code usable.
- 2026-10-24: attachments (branch `m7-attachments`). Each file has a random file key wrapped by the **item key** (context `attachmentkey:<vault>:<item>:<attachment>`), not the vault key: rotating a vault key re-wraps item keys only, so files stay readable without being touched, and a removed member who kept the old vault key already had the item keys and therefore the file keys, exactly as for item bodies. The file is encrypted with the STREAM construction (19-byte random nonce prefix, 32-bit chunk counter, last-chunk flag) bound to `attachment:<vault>:<item>:<attachment>`, so truncation, reordering, appended chunks and moving a file between items all fail. Names, types, sizes and wrapped keys live only in the encrypted item details; the server sees each file's stored size, upload time and item. Object names in storage are random. The zero-knowledge model is unchanged.

- 2026-11-02 (branch `m25-key-rotation`): Secret Key rotation, on-demand vault key rotation, emergency takeover and organiser recovery. Design first, as a maintainer decision made everything P2 and "after 1.0" part of 1.0. The takeover and organiser recovery design is in plan 06; the decisions below cover the rest, and all stay within the model above.

  - **On-demand vault key rotation** reuses the member-removal rotation (plan 15): a new vault key, every item key re-wrapped, item bodies untouched, at a new revision, in one transaction on `POST /v1/vaults/{id}/rotate`.   - **Personal vaults get a key id from their first rotation.** It was `NULL`, which turned the server's stale-key check off. A rotation sets it, so a device still on the old key gets `409 vault-key-changed` instead of storing item keys nobody can open.   - **No reauth for a vault key rotation.** It can't reveal anything or lose anything: it needs the old key and leaves the item bodies alone. The apps ask for confirmation.
  - **Security log:** `secret-key-rotated`, `vault-key-rotated` (the account that rotated, also for member removal), `emergency-takeover`, `organiser-recovery-enabled`, `organiser-recovery-disabled`.

- 2026-11-05 (maintainer decision, from testing on iPhone: "even after I open the app with Face ID, every time I need to copy or see a password it asks me again for Face ID … opening the app with Face ID is enough"): **reveal and copy ask once per unlock**, replacing "Reveal, copy and export are always gated" (2026-11-02, branch `m25-native-parity`). The rule, in every client with this gate (iPhone, iPad and Android apps, web vault, desktop app, browser and Safari extensions; the CLI has no such gate, its `--reveal` is covered by the CLI session):
  - **Covered:** when this session's unlock was the user's answer in this app or extension (device auth, or the master password, including signing in or up and creating or restoring a local vault), revealing and copying a field, showing a secret as a QR code, and showing an SSH key or environment values don't ask again. The mark is in memory only, set by the unlock screens after the unlock succeeds, and cleared by any lock (auto-lock, lock on background, Lock now, sign-out), by another account opening, and by turning the open gate off; each check also asks the vault whether it's still unlocked, so a lock the screens haven't heard about yet already counts. It also lapses when the 14-day master password check comes due while the vault stays open.
  - **Where the mark lives.** Phones: `AppModel.confirmedUnlock` (`unlockWasConfirmed`, `unlockCoversReveal`, `confirmReveal`), only counted when the open gate was on at unlock. Web vault, desktop app and the extensions' vault screens: `SessionState.confirmed` from `packages/vault-client`, read by `useConfirmReveal` in `apps/web/src/lib/identityGate.tsx`; the open gate (`requireDeviceAuthOnAppOpen`) is checked when the user reveals. The desktop app sets it when Rust reports the vault unlocked (Rust unlocks only with the master password, the device lock, or the extension's device-prompted `bridge_unlock`). The browser and Safari extensions keep it inside the session wrap in `chrome.storage.session`, so a lock, sign-out or browser close deletes both together and a wrap without it restores as unconfirmed after a worker restart; the popup reads it from the worker, never from its own storage. Firefox can't use a platform passkey in the extension, so there it counts as a device lock only where device unlock is set up.
  - **Still asks for reveal and copy** where the app or extension opened without a check: the open gate (`deviceAuthOnOpen` on the phones) off, even though the phones then ask for the master password on open; a device with no lock (the lockless rule above lets an already-unlocked vault reopen with no prompt, and plan 01's "Fill without unlocking" promises secrets still need the master password); and a session the app didn't open itself (on Android, the autofill service has its own vault and never marks the app's).
  - **Asks every time, however the vault was unlocked:** export, saving a private key or `.env` file, the Secret Key, the Recovery Kit and recovery code, master password change and reset, key rotation, account deletion, and the other Settings prompts (watch codes, local backups).
  - **Unchanged:** the one-time code a login shows still copies ungated; the AutoFill extension and Android autofill services keep asking on every fill. **The zero-knowledge model and the encryption are unchanged:** this is a local UI gate, not a key. Nothing is derived, stored or sent; the vault's keys were already in memory for the whole unlocked session, and the mark only decides whether a second prompt is shown before the app displays what it already holds.
- 2026-11-05 (maintainer decision: "saving or adding must not require unlocking"): **saving while locked**, the section above. Before this, the extension dropped a login typed while locked (`saves.ts` returned nothing when locked), addresses, cards and API keys likewise, and Android's Save opened an unlock prompt every time. Decisions made while building it: the cap (50 entries, 16 KiB each, refuse when full); the review mark (new items `Unconfirmed`, existing logins keep their mark as it is); local vaults (no ML-KEM key of their own: one derived from the ASK, nothing stored); the key pinned from the private keys at every unlock, not from the stored bundle; unreadable entries removed, failed merges kept; Android falls back to the unlocking Save screen only when no unlock has pinned a key yet or the inbox is full. Not audited, like the rest of the sealed box: covered by the review plan 09 calls for.
- 2026-11-05 (maintainer decision, plan 18, built): **stay unlocked while logged in to this device**, on by default, per device, never synced: "Stay unlocked while logged in" above, the unlock table, the two gates (which apply only while it's off) and the threat table rows "Someone at the unlocked device" and "Malware on the unlocked device". This **replaces the rule "no long-lived unguarded key copy"**: stay unlocked's key is exactly such a copy, guarded by the device's own lock instead of a prompt, which is why a lockless device can't stay unlocked. The zero-knowledge model and the server's view are unchanged; a stolen locked or powered-off device still gives only ciphertext. Rules decided while building (plan 18 History has the full list): the key is the device-unlock wrapping under a no-prompt secret per platform (desktop: the `store_unprotected` key store, which had no caller since 2026-10-27, renamed `stay-unlocked`); a session it opens isn't `confirmed`, so the first reveal asks, and on the desktop and in the extension a screen lock or sleep clears it again (with stay unlocked off, the 2026-11-05 once-per-unlock rule is unchanged); "Lock now" holds until the user unlocks or the app restarts; an organisation's auto-lock policy turns it off on that device; the desktop app answers the extension's `get-session-key-wrap` without its device-lock prompt while it stays unlocked.
- 2026-11-06 (maintainer decision, from testing on iPhone with stay unlocked off: "everything except for [export, secret key, account settings] should not ask for a password or Face ID if I already opened the app, even if the app is opened without Face ID"): **an open vault doesn't ask to reveal or copy**, replacing "reveal and copy ask once per unlock" (2026-11-05) and plan 18's "reveal and copy ask once". Before, a vault opened without the user's own answer (stay unlocked, the open gate off, turning stay unlocked off while open, a lockless device) asked on every reveal or once per screen lock. Now `unlockCoversReveal` is "the vault is unlocked" in the iPhone and Android apps and in the web code the web vault, desktop app and extension share. Someone at the unlocked device can now see secrets, not only fill them; the high-risk list still asks every time.
- 2026-11-06 (maintainer decision, plan 05 History 2026-11-06): **fill on page load**, opt-in per device in the browser extension, the one exception to "only after a gesture" in the threat row "Malicious website script reading filled values". Limited to a top-level `https://` page, a login saved for its exact host, a visible and empty login form, an unlocked vault and no fill gate that would ask. Off by default because a page's scripts (including injected ones) can read what's filled without the user doing anything.
- 2026-11-06 (maintainer decision, plan 19 History 2026-11-06): **on the Mac, Safes stay in Finder while the app runs, locked or not.** Locking still deletes every Safe key record at once and removes each Safe's File Provider domain with `.removeAll` (its plaintext copies and the names of its files go), but the app then adds the domain back empty, so Finder lists the Safe by name and the extension, with no key, answers "not authenticated"; Finder's Sign In opens the app (a File Provider UI extension with no key, which only asks the app to unlock). **What's newly visible while locked:** each Safe's name, to anyone at the Mac, in Finder's sidebar and in the system's File Provider registry; never a file's name or contents. Signing out, another account and quitting the app remove the domains, as before; a killed app is unchanged (the next launch removes them). The iPhone is unchanged: a lock removes its Safes from Files.
